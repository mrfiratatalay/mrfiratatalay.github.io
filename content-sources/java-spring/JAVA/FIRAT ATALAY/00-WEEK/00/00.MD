# PART 1 — Spring Framework neden var, Spring Boot neyi değiştiriyor?

Şimdi gerçekten başlıyoruz. Bu ilk partta henüz `@Service`, `@RestController`, `@Autowired` gibi şeylere saldırmayacağız. Önce kafamızdaki üç katmanı ayıracağız:

```
Java
  ↓
Spring Framework
  ↓
Spring Boot
```

Çünkü bu ayrım baştan oturmazsa ileride gördüğün her annotation'ı “Spring Boot özelliği” sanmaya başlarsın.

Kitabın Chapter 1'e başlarken vermeye çalıştığı ana fikir de tam olarak bu: **Spring'in tarihsel amacı Java ile uygulama geliştirmeyi daha az karmaşık hale getirmek; Spring Boot'un amacı ise Spring uygulaması geliştirirken yaşanan yapılandırma ve altyapı yükünü daha da azaltmak.** AnaChapter-01

## 1. Önce en temelden: Java nedir, Spring nedir?

Java bizim **programlama dilimiz ve platformumuz**.

Mesela ileride şöyle bir sınıf yazacağız:

```
public class OrderService {
}
```

Buradaki:

```
public
class
OrderService
```

Spring değil.

Bunların tamamı Java.

Spring'i projeden tamamen çıkarsan bile bu Java kodu yazılabilir.

Şimdi Spring Framework geldiğinde bize şunu söylüyor:

> “Sen Java class'larını yaz. Ben bunların nasıl oluşturulacağı, birbirine nasıl bağlanacağı ve yönetileceği konusunda sana yardımcı olayım.”

Yani Spring'in altında hâlâ Java var.

Bunu kafana kazı:

```
Spring, Java'nın alternatifi değildir.

Spring, Java üzerinde çalışan bir framework'tür.
```

Aynı şekilde:

```
Spring Boot da Spring'in alternatifi değildir.

Spring Boot, Spring Framework'ü kullanır.
```

Kitap bunu ileride açıkça söylüyor: **Spring Boot, Spring Framework'ün yerine geçmez; onu yoğun biçimde kullanır.** AnaChapter-01

Bu bizim için çok önemli bir cümle.

        ↓
Spring beans
        ↓
ApplicationContext
```

Spring Boot uygulaması başladığında uygulamanın çeşitli parçalarını, özellikle de classpath’i inceliyor ve gördüklerine göre ApplicationContext’e ek Spring bean’leri ekleyebiliyor. AnaChapter-01

## 1. Önce Java tarafı: Class ile Object aynı şey değil

Şöyle bir Java kodumuz olsun:

```
public class OrderService {

}
```

Bu bir **class**.

Class’ı en basit haliyle:

> Object üretmek için kullandığımız şablon / tanım

olarak düşün.

Henüz ortada gerçek bir `OrderService` nesnesi yok.

Şimdi şunu yazarsak:

```
OrderService service = new OrderService();
```

iş değişiyor.

Burada:

```
OrderService
↑
type / class

service
↑
reference variable

new OrderService()
↑
gerçek object oluşturuluyor
```

Yani class ile object arasında şu ilişki var:

```
Class
  ↓
nesnenin nasıl olacağını tarif eder

Object
  ↓
o class'tan runtime'da oluşturulmuş gerçek örnek
```

Bu ayrımı Spring için çok iyi bilmemiz gerekiyor.

Çünkü **Spring bean de sonuçta bir Java object’idir.**

---

# 2. O zaman Spring Bean nedir?

Kitabın tanımı çok önemli.

Spring uygulaması başladığında bir **ApplicationContext** oluşturur. Bu context uygulamadaki nesneleri oluşturmak, configure etmek ve onların lifecycle’ını yönetmek için container görevi görür.

Bu ApplicationContext içinde kaydedilip Spring tarafından yönetilen Java object’lerine:

> **Spring beans**

denir. AnaChapter-01

Bunu çok netleştirelim:

```
Her Spring bean
    ↓
bir Java object'idir

Ama her Java object
    ↓
Spring bean değildir
```

Örneğin:

```
OrderService orderService = new OrderService();
```

bunu kendi kodumuz içerisinde sıradan şekilde oluşturduysak:

```
Java object
```

olur.

Spring bundan haberdar olmayabilir.

Ama Spring bu nesneyi oluşturur veya onu ApplicationContext’e kaydedip yönetirse:

```
Java object
        +
Spring tarafından yönetiliyor
        ↓
Spring bean
```

olur.

Bu ayrım ileride inanılmaz önemli olacak.

# 7. Çok önemli ayrım: Spring Bean ≠ JavaBean

Kitap burada özellikle bir uyarı yapıyor.

Çünkü isimler çok benziyor:

```
Spring bean

JavaBean
```

ama bunlar aynı kavram değil.

Kitap JavaBean’i belirli bir convention izleyen Java object’i olarak anlatıyor. Örneğin alanların private olması, getter/setter sağlanması ve no-argument constructor bulunması gibi kurallardan söz ediyor. AnaChapter-01

Örneğin:

```
public class Video {

    private String name;

    public Video() {
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

Bu yapı JavaBean convention’ına yakındır.

Ama:

```
JavaBean
```

ile:

```
Spring bean
```

aynı tanım değildir.

Şunu ayır:

```
JavaBean
↓
Java dünyasındaki belirli object convention'ı

Spring Bean
↓
Spring container tarafından yönetilen Java object
```

Bu ikisinin isimlerinin benzemesi çok kişiyi karıştırır.

Sen baştan ayırmış ol.

# 9. Application açılırken zihnimizde ne oluyor?

Kitabın anlatımını sadeleştirirsek:

```
Spring application starts
        ↓
ApplicationContext oluşturulur
        ↓
Spring yönetmesi gereken object'leri belirler
        ↓
Bu object'ler oluşturulur
        ↓
Spring bean olarak context'e register edilir
        ↓
Spring bunları yönetir
```

Spring Boot tarafında ise bunun üzerine bir katman daha ekleniyor:

```
Spring Boot application starts
        ↓
classpath incelenir
        ↓
autoconfiguration kararları verilir
        ↓
gereken ek bean'ler oluşturulabilir
        ↓
ApplicationContext'e eklenir
```

Kitabın autoconfiguration için söylediği şey tam olarak bu: uygulama başlarken classpath dahil çeşitli parçaları inceleyip buna göre ApplicationContext’e ek bean’ler ekleyebilir. AnaChapter-01

## 1. “Dependency” ne demek?

İngilizce:

```
dependency = bağımlılık
```

Backend açısından ise daha kullanışlı tanım şu:

> Bir class’ın işini yapabilmek için ihtiyaç duyduğu başka bir object.

Mesela:

```
public class OrderService {

    private OrderRepository orderRepository;

}
```

Burada `OrderService`, `OrderRepository` kullanacaksa:

```
OrderService
     ↓
OrderRepository'ye ihtiyaç duyuyor
```

deriz.

Yani:

```
OrderRepository
=
OrderService'in dependency'si
```

Bunu çok iyi oturt.

Çünkü Spring’de sürekli şu cümleyi göreceksin:

> “This class has a dependency.”

Bu “bağımlılık kötü bir şey” anlamına gelmiyor.

Sadece:

> “Bu object işini yapabilmek için başka bir object’e ihtiyaç duyuyor.”

demek.

---

# 2. Spring olmadan bunu nasıl yapardık?

Normal Java ile gayet rahat yapabiliriz.

Örneğin:

```
OrderRepository repository = new OrderRepository();

OrderService service = new OrderService(repository);
```

Burada ne yaptık?

Önce:

```
new OrderRepository()
```

ile `OrderRepository` object’i oluşturduk.

Sonra:

```
new OrderService(repository)
```

ile `OrderService` object’i oluştururken repository’yi ona verdik.

Zihinsel model:

```
OrderRepository oluştur
        ↓
OrderService oluştur
        ↓
Repository'yi Service'e ver
```

Bu çalışır.

Spring olmadan da gayet düzgün Java yazabiliriz.

Dolayısıyla yine aynı uyarı:

> Spring, Java’nın yapamadığı sihirli bir şeyi mümkün hale getirmiyor.

Spring burada **object creation ve object wiring işini yönetmemize yardımcı oluyor.**

---

# 3. Küçük Java Köprüsü — constructor nedir?

Burada Java bilgin çok az olduğu için durmamız gerekiyor.

Diyelim:

```
public class OrderService {

    private OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

Buradaki:

```
public OrderService(OrderRepository repository)
```

bir **constructor**.

Constructor’ı şimdilik şöyle düşün:

> Bir object oluşturulurken çalışan özel yapı.

Biz şunu yazarsak:

```
new OrderService(repository);
```

Java gider ve şu constructor’ı çağırır:

```
OrderService(OrderRepository repository)
```

Yani `OrderService` oluşturulabilmek için diyor ki:

> “Bana bir `OrderRepository` ver.”

Dolayısıyla:

```
OrderService
        ↓
constructor
        ↓
OrderRepository istiyor
```

Burada dependency çok görünür durumda.

Bu ileride Spring’de çok hoşumuza gidecek.

---

# 4. Peki `this.repository = repository` ne?

Bunu da atlamayalım.

Şuna bak:

```
private OrderRepository repository;
```

Bu class’ın field’ı.

Sonra constructor:

```
public OrderService(OrderRepository repository) {
    this.repository = repository;
}
```

Sağdaki:

```
repository
```

constructor’a gelen parameter.

Soldaki:

```
this.repository
```

ise şu an oluşturulan `OrderService` object’inin field’ı.

Yani kabaca:

```
"Dışarıdan gelen repository object'ini,
bu OrderService object'inin repository field'ına koy."
```

Bunu yapıyoruz.

O yüzden:

```
this.repository = repository;
```

Java tarafında önemli.

Spring’e ait değil.

# 8. Dependency Injection tam olarak ne?

Şimdi tanımı oturtalım.

```
Dependency Injection
=
Bir object'in ihtiyaç duyduğu dependency'yi
kendisinin üretmesi yerine
dışarıdan alması
```

Örneğin kötü demiyorum ama sıkı bağlı bir yaklaşım:

```
public class OrderService {

    private OrderRepository repository =
        new OrderRepository();

}
```

Burada `OrderService` kendi dependency’sini kendisi yaratıyor.

Şimdi diğer yaklaşım:

```
public class OrderService {

    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

Burada `OrderService` diyor ki:

> “Ben repository yaratmıyorum. Bana bir tane ver.”

İşte zihinsel değişiklik burada.

```
Kendi dependency'ni üret

yerine

Dependency'ni dışarıdan al
```

# 9. Peki “Injection” ne demek?

Burada gerçekten iğne falan yok tabii.

> dependency’nin object’e verilmesi

anlamında kullanılıyor.

Mesela:

```

```

constructor üzerinden dependency veriyorsak:

```

```

diyoruz.

Şimdilik isim yeter:

```
Dependency Injection
        ↓
dependency dışarıdan geliyor

Constructor Injection
        ↓

```

# Önce bütün eski checkpointlerin cevapları

1. **Java ile Spring arasındaki temel fark nedir?**  
   Java bizim programlama dilimiz ve çalıştığımız platformdur. `class`, `object`, `constructor`, `interface`, `new`, `return`, `private`, `public` gibi şeyler Java’ya aittir. Spring ise Java üzerinde çalışan bir framework’tür. Java ile nesneleri ve uygulama kodunu yazarız; Spring ise bu nesnelerin oluşturulması, yönetilmesi, birbirine bağlanması gibi konularda bize altyapı sağlar. Yani `public class OrderService {}` Spring olmasa da geçerli Java’dır. `@Service` gibi Spring’e ait mekanizmaları kullanmaya başladığımızda Spring devreye girer. Spring Boot da Spring Framework’ün yerine geçmez; Spring Framework’ü kullanır ve Spring uygulamasını ayağa kaldırmayı kolaylaştırır. Kitap da bunu açıkça vurguluyor. AnaChapter-01

2. **Spring Boot, Spring Framework’ün yerine mi geçiyor?**  
   Hayır. En doğru zihinsel model `Java → Spring Framework → Spring Boot` şeklindedir. Spring Framework bize ApplicationContext, bean yönetimi, Dependency Injection gibi temel mekanizmaları sağlar. Spring Boot ise bunların kullanımını kolaylaştırır; autoconfiguration, starters, configuration properties ve dependency management gibi mekanizmalarla çok fazla manuel setup yükünü azaltır. Chapter 1’in ana konuları da zaten bunlardır. AnaChapter-01

3. **`public class OrderService` içindeki hangi kısım Java’dır?**  
   Tamamı Java’dır. `public` bir access modifier, `class` Java’daki class tanımlama keyword’ü, `OrderService` ise bizim verdiğimiz class ismidir. Burada Spring’e ait hiçbir şey yoktur. Şuna dönüşürse:

```
@Service
public class OrderService {
}
```

`public class OrderService` Java, `@Service` ise Spring tarafıdır.

4. **Spring Boot neden configuration/infrastructure yükünü azaltmak ister?**  
   Çünkü backend geliştiricisinin asıl değeri sürekli aynı web server, JSON serialization, database bağlantısı, logging veya benzeri altyapıyı tekrar tekrar elle kurmak değildir. Spring Boot yaygın altyapı kararlarına makul varsayılanlar getirerek geliştiricinin asıl business logic’e daha hızlı geçmesini amaçlar. Kitap Chapter 1’in hedefini Spring Boot’un “daha azla daha fazlasını” nasıl yaptığını göstermek olarak açıklıyor. AnaChapter-01

5. **`class` ile `object` arasındaki fark nedir?**  
   Class tanımdır, object ise o tanımdan runtime sırasında oluşturulmuş gerçek örnektir. Örneğin:

```
public class OrderService {
}
```

bir class tanımıdır. Ama:

```
OrderService service = new OrderService();
```

yazıldığında `new OrderService()` gerçek bir object oluşturur. Aynı class’tan birden fazla object üretilebilir.

6. **Her Java object bir Spring bean midir?**  
   Hayır. Spring bean olmak için object’in Spring tarafından yönetiliyor olması gerekir. `new OrderService()` ile kendi oluşturduğun sıradan bir object Spring’in haberdar olmadığı normal bir Java object’i olabilir. Spring onu ApplicationContext içerisinde kaydedip yönetiyorsa bean haline gelir.

7. **Bir Java object’i Spring bean yapan şey nedir?**  
   Object’in tipi değil, **Spring container tarafından yönetilmesi**. Spring’in ApplicationContext içerisinde oluşturduğu, configure ettiği ve lifecycle’ını yönettiği Java object’lere Spring bean denir. Kitap ApplicationContext’i nesneleri oluşturan, configure eden ve lifecycle’larını yöneten container olarak tanımlıyor. AnaChapter-01

8. **ApplicationContext’in temel görevi nedir?**  
   Uygulamadaki Spring bean’lerin merkezi yönetim ortamıdır. Bean’lerin oluşturulması, yapılandırılması, lifecycle yönetimi ve birbirlerine dependency olarak verilmesi gibi süreçlerde merkezde durur. Bunu sadece “bean listesi” gibi düşünmek yetersiz kalır; ApplicationContext Spring’in uygulamadaki object graph’ını yönettiği temel container’dır. AnaChapter-01

9. **Spring bean ile JavaBean aynı şey midir?**  
   Hayır. Spring bean, Spring container tarafından yönetilen object’tir. JavaBean ise Java dünyasındaki belirli convention’ları takip eden object yapısıdır; kitap private field, getter/setter ve no-argument constructor gibi özelliklerden bahsediyor. AnaChapter-01 İsimlerinin benzemesi seni yanıltmamalı.

10. **`new OrderService()` ile Spring’in sana `OrderService` vermesi arasındaki zihinsel fark nedir?**  
    `new OrderService()` dediğinde object creation kontrolü doğrudan senin kodundadır. Spring verdiğinde ise creation ve management sorumluluğunun önemli kısmı container’dadır. Bu da ileride dependency graph’ın merkezi şekilde yönetilmesini sağlar. Yani fark sadece syntax değil, **sorumluluğun kimde olduğu** meselesidir.

11. **`BookRepository` örneğinde dependency nedir?**  
    `DataSource`. Çünkü method:

```
bookRepository(DataSource dataSource)
```

şeklinde bir `DataSource` istiyor. `BookRepository` database bağlantı altyapısı için `DataSource`’a ihtiyaç duyuyor. Dolayısıyla `DataSource`, `BookRepository`’nin dependency’sidir. Kitabın örneği de tam olarak bunu kullanıyor. AnaChapter-01

12. **Dependency Injection ile dependency’nin class içinde `new` ile oluşturulması arasındaki fark nedir?**  
    Class kendi dependency’sini şöyle yaratırsa:

```
private OrderRepository repository = new OrderRepository();
```

dependency’yi kendisi oluşturuyor. Dependency Injection’da ise:

```
public OrderService(OrderRepository repository) {
    this.repository = repository;
}
```

diyerek ihtiyacını bildiriyor ve dependency dışarıdan geliyor. Bu, class’ı object creation detayından ayırır.

13. **Wiring nedir?**  
    Bean’lerin dependency ihtiyaçlarına göre birbirlerine bağlanmasıdır. Örneğin `OrderController → OrderService → OrderRepository → DataSource` zincirinde doğru bean’in doğru yere verilmesi wiring sürecidir. Kitap ApplicationContext’in gerekli Spring bean’leri oluşturup birbirlerine inject etmesini wiring olarak adlandırıyor. AnaChapter-01

14. **Spring olmadan Java’da Dependency Injection uygulanabilir mi?**  
    Evet. DI sadece Spring annotation’ı değildir. Örneğin:

```
OrderRepository repository = new OrderRepository();
OrderService service = new OrderService(repository);
```

Spring olmadan da dependency dışarıdan verilmiştir. Spring’in yaptığı şey bu süreci framework seviyesinde otomatikleştirmek ve büyük object graph’larda yönetmektir.

15. **Spring’in object creation işini yönetmesinin temel avantajı nedir?**  
    Kitabın verdiği temel cevap **flexibility**, yani esnekliktir. Test sırasında gerçek dependency yerine stub/mock kullanmak, farklı ortamlarda farklı implementasyonlarla çalışmak ve object creation sorumluluğunu uygulama class’larından ayırmak kolaylaşır. Kitap test ve cloud senaryolarını özellikle örnek veriyor. AnaChapter-01

16. **`new` neden kötü değildir ve IoC–DI ilişkisi nedir?**  
    `new`, Java’nın normal object oluşturma mekanizmasıdır ve kötü değildir. Problem “`new` kullanmak” değil; bir class’ın ihtiyaç duyduğu bütün application-level dependency’leri içeride kendisinin oluşturup sıkı biçimde birbirine bağlamasıdır. `OrderItem`, `Money` gibi sıradan domain object’lerini `new` ile oluşturmak son derece normaldir. IoC ise daha büyük prensiptir: application flow ve object management kontrolünün bir bölümünü framework/container’a bırakırız. DI ise bu inversion’ı gerçekleştirmek için kullanılan temel yöntemlerden biridir.

Artık Part 1–3’ün bütün açık sorularını kapattık.

# Auto-configuration

Kitap Spring Boot’un en bilinen özelliklerinden birinin autoconfiguration olduğunu açıkça söylüyor. Spring Boot uygulaması başladığında uygulamanın çeşitli bölümlerini, özellikle de **classpath’i**, inceliyor ve gördüklerine göre ApplicationContext’e ek Spring bean’leri kaydedebiliyor. AnaChapter-01

## Classpath nedir?

Java tarafında küçük bir köprü açıyoruz.

Classpath’i şimdilik:

> Java uygulamasının çalışırken erişebildiği class’ların ve library’lerin bulunduğu dünya

olarak düşün.

Mesela projemize bir JDBC/database library ekledik diyelim.

Bu library içerisinde:

```
DataSource
JDBC driver class'ları
çeşitli başka Java class'ları
```

bulunabilir.

Bunlar application’ın erişebildiği classpath’in bir parçası haline gelir.

Spring Boot da application başlarken:

> “Bu uygulamada hangi teknolojiler mevcut?”

sorusuna cevap ararken classpath’e bakabilir.

Yani:

```
dependency ekledin
      ↓
ilgili library projeye geldi
      ↓
ilgili class'lar classpath'te görünür oldu
      ↓
Spring Boot bunları tespit edebilir
```

Bu ilişkiyi ileride starter’larda çok kullanacağız.

---

# Spring Boot neye bakıyor?

Kitabın verdiği örneğe bakalım.

Kitap burada özellikle:

```

```

isminden söz ediyor. AnaChapter-01

Zihinsel akış:

```
Application başlıyor
        ↓
Spring Boot classpath'i inceliyor
        ↓
DataSource ile ilgili class mevcut
        ↓
"Demek ki bu application JDBC/database tarafını kullanıyor olabilir."
        ↓
ilgili autoconfiguration aktive ediliyor
        ↓
gereken bean'ler hazırlanabiliyor
```

Bu Spring Boot’un çok önemli davranışlarından biridir.

# Şimdi Chapter 1’in en güzel fikirlerinden biri: Backing Off

Buraya özellikle dikkat.

Spring Boot senin yerine configuration yapabiliyor.

Ama şöyle bir sorun olabilir:

> “Ben Spring Boot’un default’unu istemiyorum. Kendi `DataSource` bean’imi tanımlamak istiyorum.”

Ne olacak?

> “Hayır, benimkini kullanacaksın.”

demiyor.

Kitap burada **backing off** davranışını anlatıyor.

Eğer application içerisinde uygun bir bean’i sen zaten tanımladıysan, autoconfiguration geri çekilebilir. Kitap örneğinde H2 classpath’te olsa bile sen kendi `DataSource` bean’ini tanımlarsan Spring Boot seninkini kabul eder. AnaChapter-01

Bu çok ama çok önemli.

# Back-off zihinsel modeli

Normal durumda:

```
Sen DataSource tanımlamadın
        ↓
Spring Boot gerekli koşulları gördü
        ↓
Default DataSource bean oluşturabilir
```

Ama:

```
Sen kendi DataSource bean'ini tanımladın
        ↓
Spring Boot bunu görüyor
        ↓
"Tamam, geliştirici kararını vermiş."
        ↓
Default configuration geri çekiliyor
```

Buna:

```
back off
```

diyoruz.

Türkçeye:

> geri çekilmek

diye çevirebiliriz.

---

# Bu neden Spring Boot felsefesinin kalbi?

Çünkü Spring Boot iki uç arasında denge kurmaya çalışıyor.

Bir uç:

```
Her şeyi elle configure et.
```

Diğer uç:

```
Framework her şeyi zorla kendisi seçsin.
```

Spring Boot’un yaklaşımı:

```
Sensible defaults
        +
override edebilme özgürlüğü
```

Yani:

> “Sen bir karar vermediysen sana iyi bir default veririm. Sen açıkça karar verdiysen geri çekilirim.”

Bence Spring Boot’u tek cümleyle anlatırken aklında bulunması gereken önemli fikirlerden biri budur.

# Önce Part 4 checkpoint cevaplarını kapatalım

1. **`classpath` nedir?**  
   Classpath’i şimdilik Java uygulamasının çalışırken erişebildiği class ve library dünyası olarak düşünebilirsin. Bir dependency projeye geldiğinde onun sağladığı class’lar da uygulamanın erişebildiği alana girer. Spring Boot da uygulama başlarken bu classpath’i inceleyerek hangi teknolojilerin mevcut olduğunu anlayabilir. Kitabın `DataSource` örneğinde yaptığı tam olarak budur. AnaChapter-01

2. **Autoconfiguration neyi otomatikleştiriyor?**  
   Spring Boot, belirli koşullara bakarak bizim elle yazmak zorunda kalabileceğimiz bazı Spring configuration’larını ve bean tanımlarını otomatik olarak devreye sokabiliyor. Örneğin JDBC/DataSource tarafının mevcut olduğunu anlarsa uygun `DataSource` configuration’ını hazırlayabiliyor. AnaChapter-01

3. **`@ConditionalOnClass(DataSource.class)` kabaca ne demek?**  
   “Classpath’te `DataSource` class’ı varsa bu configuration değerlendirilebilir” demektir. Yani configuration koşulsuz değildir; ilgili teknoloji gerçekten application’da mevcutsa devreye girmeye aday olur. AnaChapter-01

4. **`DataSourceAutoConfiguration` neden her application’da körü körüne çalışmıyor?**  
   Çünkü autoconfiguration conditional çalışır. Spring Boot 4’te bu politikalar belirli teknoloji ve framework’lere göre organize edilir ve bean’ler yalnızca gerekli koşullar oluştuğunda register edilir. AnaChapter-01

5. **Back-off ne demek?**  
   Spring Boot default bir bean sağlamaya hazırlanmış olsa bile sen kendi bean’ini tanımladıysan geri çekilebilmesidir. Kitabın örneğinde H2 classpath’te olsa bile sen kendi `DataSource` bean’ini register edersen Spring Boot onu kabul eder ve kendi varsayılan çözümünü zorlamaz. AnaChapter-01

6. **Autoconfiguration ile Dependency Injection aynı şey mi?**  
   Hayır. Autoconfiguration uygun bean/configuration’ların oluşturulmasına karar verir. Dependency Injection ise mevcut dependency’lerin onları isteyen bean’lere verilmesidir. Örneğin autoconfiguration bir `DataSource` bean oluşturabilir; sonra DI bu `DataSource` bean’ini `BookRepository`’ye verebilir.

7. **Starter ile autoconfiguration aynı şey mi?**  
   Hayır. Starter birazdan işleyeceğimiz gibi belirli bir functionality için gerekli dependency grubunu projeye eklemeyi kolaylaştırır. Autoconfiguration ise classpath ve koşullara göre configuration/bean kararları verir. Fakat birbirleriyle çok sıkı bağlantılıdırlar.

8. **`dependency → classpath → condition → autoconfiguration → bean → ApplicationContext` zinciri ne anlatıyor?**  
   Bir dependency projeye eklenir. Onun class’ları classpath’e gelir. Spring Boot bu class’ları görür ve conditional configuration’ları değerlendirir. Koşullar sağlanırsa ilgili autoconfiguration devreye girebilir. Bu configuration gerekli Spring bean’lerini oluşturabilir. Bu bean’ler de ApplicationContext içinde yönetilir.

İşte şimdi Part 5’e hazırız.

# Önce Part 5 checkpoint cevaplarını kapatalım

Söz verdiğimiz düzende ilerliyoruz: önce önceki partın bütün soruları, sonra yeni konu.

1. **Starter hangi problemi çözüyor?** Bir functionality için gereken ilişkili dependency’leri tek tek araştırıp ekleme yükünü azaltıyor. Örneğin web application geliştirmek için gerekli parçaları ayrı ayrı seçmek yerine `spring-boot-starter-webmvc` ekleyebiliyoruz. Kitap starter’ları belirli bir functionality alanını temsil eden, özenle seçilmiş mantıksal dependency grupları olarak tanımlıyor. AnaChapter-01

2. **Starter ile normal dependency arasındaki ilişki nedir?** Starter’ın kendisi de build dosyamıza eklediğimiz bir dependency’dir; ancak temel amacı tek bir library’nin işlevini sunmaktan çok, belirli bir capability için gereken ilişkili dependency set’ini projeye getirmektir. Yani kabaca `starter → bir grup dependency`.

3. **`spring-boot-starter-webmvc` bize ne söylüyor?** Uygulamamızın Spring MVC tabanlı, servlet modelini kullanan bir web application olacağını açıkça ifade ediyor. Buna karşılık WebFlux starter reactive/non-blocking stack’i temsil ediyor. Kitap Spring Boot 4’te bu explicit seçimin architectural intent’i build configuration’da görünür kıldığını vurguluyor. AnaChapter-01

4. **WebMVC starter önemli olarak neler getiriyor?** Kitap Spring MVC ve ortak Spring Web altyapısı, Jackson üzerinden JSON serialization/deserialization, embedded servlet container, validation/error-handling altyapısı, logging/configuration desteği ve MVC’ye özel autoconfiguration’ı sayıyor. AnaChapter-01

5. **Starter ile autoconfiguration neden aynı şey değil?** Starter dependency tarafındadır: gerekli teknolojileri projeye getirir. Autoconfiguration ise uygulamada hangi teknolojilerin mevcut olduğuna ve çeşitli koşullara bakıp configuration/bean kararları verir. Starter classpath’i değiştirir; değişen classpath autoconfiguration’ı etkileyebilir.

6. **`starter → dependency → classpath → autoconfiguration` zinciri nasıl çalışıyor?** Starter eklendiğinde ilgili dependency’ler gelir. Onların class’ları classpath’te görünür olur. Spring Boot application başlarken classpath’i ve condition’ları inceler. Uygun autoconfiguration aktive olabilir ve bunun sonucunda gerekli infrastructure bean’leri oluşturulabilir.

7. **Spring MVC ile WebFlux arasındaki temel farkı şimdilik nasıl ifade ediyoruz?** Spring MVC klasik servlet tabanlı web programming modelidir. WebFlux ise reactive/non-blocking web applications için tasarlanmıştır. Şu an WebFlux’un iç mekanizmasını öğrenmiyoruz; bizim temel backend eğitimimizin ilk yolu MVC olacak. AnaChapter-01

8. **Starter ile dependency management arasındaki fark nedir?** Starter daha çok “hangi dependency ailesine ihtiyacım var?” sorusuyla ilgilenir. Dependency management ise “bunların hangi sürümleri birlikte uyumlu çalışmalı?” problemini çözer. Chapter’ın son bölümünde bunu ayrıca öğreneceğiz.

9. **Transitive dependency nedir?** Sen doğrudan `A` library’sini eklersin ama `A`, çalışmak için `B` ve `C` library’lerine ihtiyaç duyar. Build sistemi onları da getirirse `B` ve `C`, senin açısından transitive dependency’lerdir. Yani doğrudan istemedin; istediğin başka dependency üzerinden geldiler.

10. **Neden starter’ları “Spring magic” diye ezberlemiyoruz?** Çünkü ileride bir şey bozulduğunda “starter ekledim ama neden çalışmıyor?” sorusuna cevap verebilmek için alttaki zinciri bilmen gerekir:

```
Starter
   ↓
Dependencies
   ↓
Classpath
   ↓
Conditions
   ↓
Autoconfiguration
   ↓
Beans
   ↓
ApplicationContext
```

İşte artık bu bölüm tamamen kapanmış durumda.

# 13. Getter ve setter neden tekrar çıktı?

Kitap class’ın standard JavaBean property rules’a uymasından ve getter/setter’lardan bahsediyor. AnaChapter-01

```
private String header;
```

private olduğu için dışarıdan doğrudan erişimi sınırlı.

Getter:

```

    return header;
}
```

değeri okumamıza yarar.

Setter:

```
public void setHeader(String header) {
    this.header = header;
}
```

değeri değiştirmeye yarar.

Henüz encapsulation konusunu Core Java seviyesinde detaylı işlemedik. Ama şimdilik şunu bil:

```
field
        ↓
private data

getter
        ↓
oku

setter
        ↓
değer ata/değiştir
```

Kitabın verdiği klasik `@ConfigurationProperties` örneği bu JavaBean yaklaşımını kullanıyor.

Kitap modern Java için küçük ama önemli bir not düşüyor:

```

```

veya:

```

```

ile register edilmesini söylüyor.

Bunu şu an ezberlemeyeceksin.

Çünkü daha:

```
record nedir?
```

konusunu Java tarafında düzgün öğrenmedik.

Şimdilik sadece:

```
@ConfigurationProperties
yalnızca klasik getter/setter class'larıyla sınırlı değil;
modern Java record yaklaşımı da mümkün.
```

bilmen yeterli.

## 1. Externalized configuration ne demektir ve neden gereklidir?

Externalized configuration, uygulamanın çalışması için gereken bazı ayarların doğrudan Java kaynak kodunun veya application artifact'ının içine gömülmek zorunda olmaması demektir.

```

```

```

API bilgileri
server ayarları
environment'a özel değerler
```

farklı olabilir.

Dolayısıyla istediğimiz:

```
AYNI CODE
   +
FARKLI CONFIGURATION
   ↓
FARKLI ENVIRONMENT'LARDA ÇALIŞMA
```

Kitap Spring Boot'un yalnızca JAR içine paketlenmiş `application.properties` dosyasını değil, application'ın çalıştırıldığı dizindeki external configuration dosyalarını da yükleyebildiğini; böylece paketlenmiş değerlerin dışarıdan override edilebildiğini anlatıyor. AnaChapter-01

## 2. Internal ve external `application.properties` arasındaki fikir farkı nedir?

```

        ↓

```

        ↓

```

```

→ application ile beraber paketlenebilir

External config
→ deploy edilen aynı application'ı değiştirmeden
  ortamdan ortama farklı değer sağlayabilir
```

## 6. Property precedence neden gereklidir?

Çünkü aynı property birden fazla yerde bulunabilir.

Düşün:

```
application.properties
server.port=8080
```

ama environment:

```
server.port=9000
```

diyor olabilir.

Spring Boot'un:

> Hangisi geçerli?

sorusuna deterministic bir cevap vermesi gerekiyor.

Bu nedenle configuration source'larının bir precedence, yani **öncelik sırası** vardır. Kitap config files, OS environment variables, Java system properties, command-line arguments ve test configuration gibi çeşitli source'ları düşükten yükseğe doğru bir sıra içinde gösteriyor. AnaChapter-01

Bütün sırayı ezberlemiyoruz.

Ama prensip:

```
aynı key
+
birden fazla source
        ↓
precedence uygulanır
        ↓
effective value belirlenir
```

## 7. Aynı property birden fazla yerde bulunursa ne olur?

```
Düşük öncelik:

Daha yüksek öncelik:

server.port = 9000
```

Buradaki:

```

```

application'ın gerçekten kullanacağı son değerdir.

## 8. `@ConditionalOnProperty` ne işe yarar?

Configuration property'sine göre bir Spring bean'in oluşturulup oluşturulmamasını kontrol edebilir.

Örneğin:

```
@Bean
@ConditionalOnProperty(
    prefix = "my.app",
    name = "video"
)
YouTubeService youTubeService() {
    return new YouTubeService();
}
```

Kitap burada `my.app.video` property'sinin bulunmasını bean creation için condition haline getiriyor. Property mevcutsa `YouTubeService` bean'i oluşturulabilir; yoksa oluşturulmaz. AnaChapter-01

Böylece property artık yalnızca:

```

database URL ne?
```

demekle kalmıyor.

Şunu bile etkileyebiliyor:

```
ApplicationContext'te
hangi bean bulunacak?
```

---

# 1. Önce `version` problemi nedir?

Bir library düşün:

```
Spring Data JPA
```

Bunun:

```
Version A
Version B
Version C
```

gibi farklı release'leri olabilir.

Başka bir library:

```
Spring Framework
```

onun da ayrı sürümleri var.

Spring Security:

```
Spring Security X
Spring Security Y
```

gibi ilerliyor.

Problem şu:

```
Spring Framework version A
+
Spring Data JPA version B
+
Spring Security version C
+
Hibernate version D
```

kombinasyonu gerçekten uyumlu mu?

Bunu geliştirici olarak tek tek çözmek zorunda kalsan çok yorucu olur.

---

# 2. Neden “en yeni olanı seçerim” diyemeyiz?

Çünkü:

```
latest ≠ otomatik olarak compatible
```

Bir library'nin yeni version'ını yükselttiğinde o library:

```
başka API'lere
başka framework version'larına
başka third-party dependency'lere
```

bağlı olabilir.

Kitap burada Spring Data JPA'yı upgrade etmek isteyen bir geliştirici örneği kullanıyor ve ardından şu problemi çıkarıyor:

```
Spring Data JPA'yı yükselttim.

Spring Framework ne olacak?

Spring MVC?

Spring Integration?

Diğer dependencies?
```

Yani tek dependency upgrade'i bütün dependency graph'ı etkileyebilir. AnaChapter-01

Bu gerçek bir maintenance problemidir.

# 18. Configuration Property nedir?

# En kritik 10 cümle

Bunları anlayabiliyorsan chapter gerçekten oturmuştur:

1. **Spring bean normal bir Java object'idir; farkı Spring tarafından yönetilmesidir.**
2. **ApplicationContext Spring'in bean container'ıdır.**
3. **Dependency Injection, object'in dependency'sini kendi oluşturmaması, dışarıdan almasıdır.**
4. **Spring Boot, Spring Framework'ün yerine geçmez; onu kullanır.**
5. **Autoconfiguration classpath ve başka koşullara göre uygun configuration'ları devreye sokabilir.**
6. **Starter belirli functionality için gereken dependency set'ini kolayca getirir.**
7. **Configuration properties Spring Boot default'larını değiştirmemize ve custom configuration oluşturmamıza izin verir.**
8. **Externalized configuration aynı application'ı farklı environment'larda farklı değerlerle çalıştırmamızı sağlar.**
9. **Configuration hangi bean'lerin oluşacağını bile etkileyebilir.**
10. **Spring Boot dependency management/BOM, dependency version uyumluluğu yükünü büyük ölçüde azaltır.**
