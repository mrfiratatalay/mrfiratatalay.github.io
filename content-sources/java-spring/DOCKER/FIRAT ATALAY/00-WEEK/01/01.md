**Önce ne geliştirdiğimizi gözünde canlandıralım.**

Bu bölüm boyunca küçük bir video uygulaması geliştireceğiz. Başlangıçta bir web sayfası gösterecek, ardından videoları listeleyecek ve yeni video eklemeyi öğreneceğiz.

Tarayıcı, bizim Java dosyalarımızı açıp incelemiyor. Sunucuya **HTTP isteği** gönderiyor. Sunucudaki uygulama bu isteği işliyor ve bir **HTTP cevabı** gönderiyor.

Bu cevap, tarayıcının göstereceği HTML içeriği olabilir. İlerleyen partlarda oluşturacağımız API’de ise JSON verisi olacak.

Bu bağımlılıklar sayesinde controller annotation’larına, HTTP isteklerini eşleme altyapısına ve ileride kullanacağımız JSON dönüştürme desteğine ulaşacağız.

**Artık ilk controller’ımızı yazabiliriz.**

Bir **web controller**, belirli HTTP isteklerini karşılamak üzere tanımladığımız uygulama bileşenidir.

Örneğin ileride:

- Ana sayfa isteğini karşılayabilir.
- Video listesini döndürebilir.
- Gönderilen yeni video bilgisini alabilir.

Şimdi yalnızca ana sayfa isteğini ele alacağız.

`com.learningspringboot4` paketi içinde **`HomeController.java`** dosyasını oluştur:

```
package com.learningspringboot4;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class HomeController {

    @GetMapping("/")
    public String index() {
        return "index";
    }
}
```

Şimdi bu kodu acele etmeden açalım.

**İlk satır, sınıfın hangi pakete ait olduğunu söylüyor.**

```
package com.learningspringboot4;
```

Java’da paketler, sınıfları düzenlememizi ve isimlerini birbirinden ayırmamızı sağlar.

Bu sınıfın tam adı:

```
com.learningspringboot4.HomeController
```

Projede kaynak dosyasının konumu da normalde şu yapıya karşılık gelir:

```
src/main/java/com/learningspringboot4/HomeController.java
```

Controller’ı uygulamanın başlangıç sınıfıyla aynı pakete yerleştirmemiz ayrıca Spring açısından da işimize yarıyor. Varsayılan component scanning, başlangıç sınıfının bulunduğu paketi ve alt paketlerini kapsar. Bu nedenle başlangıç sınıfını uygulamanın kök paketinde tutmak önerilir. [docs.spring.io](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html?utm_source=chatgpt.com)

**Ardından kullandığımız Spring tiplerini belirtiyoruz.**

```
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
```

`import`, başka paketteki bir tipi kodumuzda kısa adıyla kullanmamızı sağlar.

Örneğin ilk import sayesinde annotation’ı uzun adıyla yazmak yerine:

```
@Controller
```

şeklinde kullanabiliyoruz.

Burada iki ayrı iş var:

**Maven bağımlılığı**, ilgili kütüphaneyi projede kullanılabilir hâle getiriyor.  
**Java import’u**, o kütüphanedeki tipe kaynak kodda kısa adıyla başvurmamızı sağlıyor.

Bu ayrımı erken öğrenmen işini çok kolaylaştıracak.

**Şimdi Java sınıfımızı tanımlıyoruz.**

```
public class HomeController {
    // Sınıfın içeriği
}
```

`class`, bir sınıf tanımladığımızı belirtiyor. `HomeController` ise bu sınıfa verdiğimiz isim.

Sınıf, oluşturulabilecek nesnelerin yapısını ve davranışlarını tanımlar. **Nesne**, bu sınıftan oluşturulan somut örnektir.

Burada sınıfımıza bir davranış ekleyeceğiz: `index()` metodu.

`public`, bu sınıfın diğer paketlerden de erişilebilir olmasını sağlayan Java erişim belirleyicisidir. **HTTP erişim izni veya güvenlik ayarı anlamına gelmez.**

Dıştaki `{` ve `}` işaretleri, sınıfın gövdesini sınırlar.

**Metodun Java tarafını Spring’den ayrı okuyalım.**

```
public String index() {
    return "index";
}
```

Bu küçük parçada:

| İfade             | Java açısından anlamı                                |
| ----------------- | ---------------------------------------------------- |
| `public`          | Metodun erişim belirleyicisi                         |
| `String`          | Metodun döndürdüğü değerin tipi                      |
| `index`           | Metodun adı                                          |
| `()`              | Bu metodun parametre almadığı                        |
| `{ ... }`         | Metodun çalıştıracağı kod                            |
| `return "index";` | Metodu bitirip `"index"` değerini çağırana döndürmek |

`String`, Java’da metin değerlerini temsil eden tiptir. Çift tırnak içindeki `"index"` ise bir metin değeridir.

Burada aynı kelimenin iki ayrı görevde kullanıldığına dikkat et:

```
index()
```

bir **metot adı**.

```
"index"
```

bir **metin değeri**.

Bu ikisinin aynı yazılması zorunlu değil. Birazdan nedenini göreceğiz.

**Şimdi Spring’in bu sınıfı nasıl tanıdığına gelelim.**

```
@Controller
```

Bu ifade bir **annotation**.

Annotation’lar, kodun belirli parçalarına eklenen bilgilerdir. Burada Spring’in okuyup anlamlandırdığı bir annotation kullanıyoruz.

`@Controller`, bu sınıfın web controller rolünde olduğunu belirtir. Component scanning sırasında Spring tarafından bulunmasına ve uygulamanın yönettiği bileşenlerden biri olmasına imkân verir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann.html?utm_source=chatgpt.com)

Spring’in oluşturup yönettiği bu nesnelere **bean** diyoruz. Bunların yönetildiği temel yapı da **application context**.

Şimdilik şu bağlantıyı kurman yeterli:

> **Sınıfı biz yazıyoruz. Bu örnekte controller nesnesinin oluşturulmasını ve Spring uygulamasına dahil edilmesini Spring yönetiyor.**

Nesnelerin birbirine bağlanmasını Part 3’te ayrıntılı işleyeceğiz.

**Bir sonraki annotation, isteği metodumuzla eşliyor.**

```
@GetMapping("/")
```

Bu tanım, uygulamanın kök yoluna gelen HTTP GET isteğini aşağıdaki metotla ilişkilendiriyor:

```
public String index()
```

Örneğin varsayılan yerel çalışma adresimiz şöyle olsun:

```
http://localhost:8080/
```

Bu adreste:

- `http`, iletişim protokolü.
- `localhost`, isteği yapan bilgisayarın kendisi.
- `8080`, uygulamanın dinlediği port.
- `/`, istenen yol; burada kök yol.

Tarayıcının adres çubuğundan bu sayfayı istediğimizde normalde bir **GET isteği** gönderilir.

Spring MVC, mapping tanımımızdan bu isteği hangi controller metodunun karşılayacağını belirler. `@GetMapping`, HTTP metoduna özel mapping annotation’larından biridir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html?utm_source=chatgpt.com)

Burada küçük ama değerli bir ayrım daha var:

**HTTP metodu:** `GET`  
**Java metodu:** `index()`

İkisine de “metot” diyoruz, fakat farklı kavramlar.

HTTP metodu isteğin türünü belirtirken Java metodu uygulamanın çalıştırdığı kod parçasıdır.

**Metodun ismini değiştirmek, tek başına URL’yi değiştirmez.**

Şunu yazsaydık:

```
@GetMapping("/")
public String home() {
    return "index";
}
```

Yine `/` yoluna gelen GET isteği karşılanırdı.

Çünkü burada HTTP eşleşmesini belirleyen bilgi:

```
@GetMapping("/")
```

Metot isimlerini ise kodun amacını anlaşılır kılacak şekilde seçiyoruz. Bu yüzden `index()` veya `home()` gibi anlamlı isimler kullanmak yararlı.

**🔴 Şimdi en önemli satıra geldik: `return "index";` ne yapıyor?**

Bunu iki katmanda düşünmeni istiyorum.

**Java açısından:** Metot, kendisini çağıran koda `"index"` metnini döndürür.

**Bu controller’ın Spring MVC bağlamında:** Dönen metin, gösterilecek **view’ın mantıksal adı** olarak yorumlanır.

Yani Spring MVC bu örnekte şunu anlar:

> “`index` isimli görünümü bul ve cevabı bu görünüm üzerinden oluştur.”

Buradaki **view**, kullanıcıya gösterilecek görünüm demek. Bir sonraki partta bunun için bir HTML şablonu hazırlayacağız. Spring MVC’nin view çözümleme mekanizması, dönen ismi uygun görünümle eşleştirecek. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/return-types.html?utm_source=chatgpt.com)

Dolayısıyla bu örnekte `"index"` değeri, doğrudan tarayıcıda yazdırmak istediğimiz bir mesaj olarak kullanılmıyor.

Aynı `String` değerinin farklı controller düzenlerinde farklı biçimde işlenebildiğini ilerleyen partlarda göreceğiz. Şu anki davranışı anlaman için bağlamımız önemli: **`@Controller` kullanan ve view adı döndüren bir metot yazdık.**

**🧠 Burada kısa bir mühendislik parantezi açalım: İstek controller’a nasıl ulaşıyor?**

Uygulamayı çalıştırdığımızda web sunucusu da başlatılır. Seçtiğimiz standart web başlangıcında bu rolü gömülü Tomcat üstlenir.

HTTP isteği önce bu sunucuya ulaşır. Servlet işleme akışından, varsa ilgili filtrelerden geçerek Spring MVC’nin merkezindeki **`DispatcherServlet`** bileşenine gelir.

`DispatcherServlet`, isteğin işlenmesini koordine eder. Eşleme ve çağırma işlerinde yardımcı bileşenlerden yararlanarak uygun controller metodunu çalıştırır. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html?utm_source=chatgpt.com)

Burada controller’ın rolü, **kendisine yönlendirilen isteği uygulama kodumuzla karşılamak**.

Bu nedenle `HomeController` içinde port dinleyen veya HTTP bağlantısını elle kabul eden kod yazmadık. Bu görevler altyapı bileşenlerinde.

Bir de iki zamanı birbirinden ayıralım:

- **Uygulama başlarken:** Spring bileşenleri ve istek eşlemelerini hazırlar.
- **İstek geldiğinde:** Hazırlanan eşleme kullanılarak uygun metot çalıştırılır.

Bunu anlaman, ileride “Bu kod uygulama açılırken mi çalışıyor, her istekte mi çalışıyor?” sorusunu doğru sormanı sağlayacak.

**Peki şu anda tarayıcıda tamamlanmış bir sayfa görebilir miyiz?**

Henüz `index` görünümünü oluşturmadık. Şablon motorunu da eklemedik.

Controller’ın hangi isteğe karşılık hangi görünüm adını döndüreceğini belirledik; **görünümü oluşturacak parçayı Part 2’de tamamlayacağız.**

Bu aşamada uygulamanın başlayabilmesiyle `/` isteğine istediğimiz HTML sayfasını verebilmesi iki ayrı başarı ölçütü. Ana sayfada hata görürsen bunu hemen “Controller kodunu yanlış yazdım” şeklinde yorumlama; eksik olan görünüm adımını da düşün.

**Bugünden yanında götürmeni istediğim beş bilgi var.**

- **Initializr**, başlangıç proje dosyalarını hazırlar.
- **Maven ve `pom.xml`**, bağımlılıkları ve build sürecini yönetir.
- **`@Controller`**, sınıfımızın web controller rolünü belirtir.
- **`@GetMapping("/")`**, kök yola gelen GET isteğini metodumuzla eşler.
- **`return "index"`**, bu örnekte Spring MVC’ye görünüm adını verir.

✍️ **Küçük uygulaman:** Projeyi açıp `HomeController` kodunu kendin yaz. Ardından her satırın yanına kendi cümlenle ne yaptığını açıklayan kısa bir yorum ekle. Özellikle `@GetMapping`, `String`, `index()` ve `"index"` ifadelerini birbirinden ayır.

Şimdi de üç kontrol sorumuz:

3. `return "index";` satırı **Java açısından** ne yapar, **bu Spring MVC örneğinde** nasıl yorumlanır?

**Sayfada üç videoyu göstermek istiyoruz.**

Videoların isimlerini doğrudan HTML’e yazabiliriz. Fakat öğrenmek istediğimiz asıl bağlantı, uygulamadaki verinin sayfaya aktarılması.

Bunun için önce Java tarafında videoyu temsil edecek bir tip oluşturacağız:

```
record Video(String name) {}
```

Burada biraz duralım. Bu satırı anlayarak ilerlememiz önemli.

**`record`, Java’nın bir özelliği.**

Bir `record`, veriyi belirli bileşenlerle temsil etmek için kullanabildiğimiz özel bir sınıf biçimidir.

Şu tanımı okuyalım:

```
record Video(String name) {}
```

- `record`: Bir record tanımlıyoruz.
- `Video`: Tanımladığımız tipin adı.
- `String`: Bileşenin tipi.
- `name`: Bileşenin adı.
- `{}`: Ek metot yazabileceğimiz gövde; şu an boş.

Yani şunu söylüyoruz:

> “Uygulamamda `Video` diye bir veri tipi var. Her video bir isim taşıyor.”

Java derleyicisi bu tanıma göre gerekli temel yapıları oluşturur. Bunların arasında nesneyi oluşturacak constructor ve `name()` erişim metodu bulunur. Ayrıca `toString()`, `equals()` ve `hashCode()` metotları da sağlanır.

Bugün özellikle **nesnenin oluşturulması ve verisinin okunması** üzerinde duracağız.

**Tipi tanımlamakla nesne oluşturmak iki ayrı işlem.**

Şu satır bir tip tanımı:

```
record Video(String name) {}
```

Şu ifade ise o tipten bir nesne oluşturuyor:

```
new Video("Spring Boot öğreniyorum")
```

`new`, yeni nesnenin oluşturulmasını başlatır. `Video(...)` constructor çağrısıyla, oluşturulan videonun başlangıç bilgisi verilir.

**Constructor**, nesne oluşturulurken başlangıç durumunu hazırlamak için kullanılan yapıdır. Burada verdiğimiz metin, videonun `name` bileşeninin değeri olur.

Bu nesneyi bir değişken üzerinden kullanabiliriz:

```
Video video = new Video("Spring Boot öğreniyorum");
```

Satırı parçalara ayıralım:

| Parça            | Anlamı                                               |
| ---------------- | ---------------------------------------------------- |
| Soldaki `Video`  | Değişkenin tipi                                      |
| `video`          | Değişkenin adı                                       |
| `new Video(...)` | Yeni nesnenin oluşturulması                          |
| `=`              | Oluşturulan nesnenin referansının değişkene atanması |

Buradaki `video` değişkeni, oluşturduğumuz nesneye referans verir.

İsmi okumak istediğimizde:

```
String videoAdi = video.name();
```

yazabiliriz.

Dikkat et: Record’un otomatik erişim metodunun adı **`name()`**. Otomatik olarak `getName()` isimli bir metot üretilmez.

**Record’un değişmezliği konusunda da doğru bir temel kuralım.**

Record bileşenlerinin alanları `final` olur. Bu örnekte oluşturduğumuz videonun `name` alanını sonradan başka bir değere atayamayız.

Fakat bir record’un içinde değiştirilebilir bir nesne bulunursa, o nesnenin içeriği ayrıca değişebilir. Dolayısıyla record kullanmak, içindeki bütün nesneleri otomatik olarak dondurmaz.

Bizim örneğimizde bileşen `String` olduğu için durum sade.

**Şimdi tek videodan video listesine geçelim.**

Üç videoyu birlikte tutmak için:

```
List<Video> videos = List.of(
    new Video("Need HELP with your SPRING BOOT 4 App?"),
    new Video("Don't do THIS to your own CODE!"),
    new Video("SECRETS to fix BROKEN CODE!")
);
```

yazıyoruz.

Buradaki yeni ifade:

```
List<Video>
```

Bunu şöyle oku:

> “Eleman tipi `Video` olan bir liste.”

`List`, Java’nın liste davranışını tanımlayan arayüzüdür. **Arayüz**, burada bir liste üzerinden hangi işlemlerin kullanılabileceğini belirleyen sözleşme gibi düşünülebilir. Somut liste nesnesini ise `List.of(...)` sağlıyor.

`<Video>` kısmı **generic tip bilgisi**. Derleyiciye, bu listenin elemanlarının `Video` olması gerektiğini söylüyor.

Böylece listeden bir eleman aldığımızda onun hangi tipte olduğunu biliyoruz. Yanlışlıkla farklı tipte bir nesne eklemeye çalıştığımızda da Java bunu denetleyebiliyor.

**`List.of(...)`, verdiğimiz elemanlarla bir liste oluşturuyor.**

Parantezin içindeki her `new Video(...)` bir video nesnesi oluşturur. `List.of(...)` bu elemanları verdiğimiz sırayla bir araya getirir.

`of`, `List` tipi üzerinden çağırdığımız statik bir metottur. Kullanmak için önceden ayrı bir liste nesnesi oluşturmamız gerekmez.

Burada önemli bir özellik var: **`List.of()` ile elde edilen listenin eleman yapısı değiştirilemez.** Bu listeye sonradan `add()` ile eleman eklemeye veya `remove()` ile eleman silmeye çalışmak `UnsupportedOperationException` oluşturur. Listenin içindeki nesnelerin kendi değişebilirliği ise ayrı konudur. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html?utm_source=chatgpt.com)

Şimdilik listeyi yalnızca göstereceğiz. Veri eklemeye geçtiğimiz Part 4’te bu özellik yeniden karşımıza çıkacak.

**Artık controller’ımızın güncel hâlini yazalım.**

`HomeController.java` dosyamız şöyle olacak:

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class HomeController {

    record Video(String name) {}

    List<Video> videos = List.of(
        new Video("Need HELP with your SPRING BOOT 4 App?"),
        new Video("Don't do THIS to your own CODE!"),
        new Video("SECRETS to fix BROKEN CODE!")
    );

    @GetMapping("/")
    public String index(Model model) {
        model.addAttribute("videos", videos);
        return "index";
    }
}
```

Bu aşamada `Video` tipini controller’ın içinde tanımlıyoruz. Ayrıca `videos`, metodun dışında tanımlandığı için controller nesnesinin bir **alanı**, yani *field*.

Bu örnekte controller nesnesi oluşturulurken başlangıç listesi de hazırlanır. `index()` çağrıldığında mevcut liste kullanılır.

Part 3’te bu verinin ve veriyle ilgili işlemlerin yerini düzenleyeceğiz. Şimdi önce veri aktarımını tamamlayalım.

**🔴 Java listesini şablona taşıyan köprü: `Model`.**

Metodumuzun önceki hâli şuydu:

```
public String index()
```

Şimdi şöyle:

```
public String index(Model model)
```

`Model`, Spring MVC’nin görünüm oluşturulurken kullanılacak verileri taşımamıza sunduğu yapıdır.

Burada import ettiğimiz tip:

```
import org.springframework.ui.Model;
```

Spring MVC, controller metodunu çağırırken uygun `Model` nesnesini parametre olarak sağlar. Biz de şablona aktaracağımız bilgileri bunun içine ekleriz. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/arguments.html?utm_source=chatgpt.com)

Şu satıra bakalım:

```
model.addAttribute("videos", videos);
```

Bu satır, modele **isim verilmiş bir veri** ekliyor.

İki argümanı var:

```
"videos"
```

Şablonun bu veriye erişirken kullanacağı **isim**.

```
videos
```

Controller alanında tuttuğumuz **gerçek Java listesi**.

Tırnaklı ifadeyle tırnaksız ifade farklı görevlerde.

Bunu küçük bir örnekle daha belirginleştirelim:

```
model.addAttribute("videoListesi", videos);
```

Burada Java’daki değişkenin adı yine `videos`. Ancak şablona sunduğumuz isim artık `videoListesi`.

Demek ki Java değişkeninin adıyla model attribute’unun adı aynı olmak zorunda değil. Şablonun kullanacağı isim, **tırnak içinde verdiğimiz anahtar**.

Biz ana örneğimizde şu satırla devam ediyoruz:

```
model.addAttribute("videos", videos);
```

**Controller artık görünüm için iki ayrı bilgi sağlıyor.**

| Bilgi                       | Nasıl sağlanıyor?                      |
| --------------------------- | -------------------------------------- |
| Görünümde kullanılacak veri | `model.addAttribute("videos", videos)` |
| Kullanılacak görünümün adı  | `return "index"`                       |

Bu ayrımı iyi oturtmanı istiyorum.

`return "index"` ile listeyi döndürmüyoruz. Listeyi modele ekliyoruz; dönüş değeriyle hangi görünümün kullanılacağını belirtiyoruz.

Bu noktada verilerimiz hâlâ Java nesneleri. Bu HTML üretme akışında videoları önce JSON’a çevirmemiz gerekmiyor.

**Sırada şablonun bu veriyi kullanması var.**

`index.mustache` dosyasındaki paragrafın altına şunu ekle:

```
<ul>
    {{#videos}}
        <li>{{name}}</li>
    {{/videos}}
</ul>
```

Şimdi üç Mustache ifadesini açalım.

```
{{#videos}}
```

Modelde `videos` adıyla bulunan veriyle bir **section**, yani bölüm açar.

Bu veri bir liste olduğu için Mustache, bölümün içeriğini listedeki her eleman için tekrar işler.

```
{{name}}
```

O anda işlenmekte olan elemanın `name` değerini gösterir.

```
{{/videos}}
```

Bölümü kapatır.

Bizim listemizde üç eleman olduğuna göre şu parça üç kez üretilecek:

```
<li>{{name}}</li>
```

İlk seferinde ilk videonun adı, ikinci seferinde ikinci videonun adı, üçüncü seferinde üçüncü videonun adı kullanılacak.

Buradaki önemli ayrıntı şu: **Bölümün içinde `{{name}}`, sıradaki `Video` nesnesinin verisine bakıyor.**

**Peki Mustache, record’un `name` bilgisini nasıl okuyor?**

Az önce Java tarafında şunu kullandık:

```
video.name()
```

Mustache tarafında ise:

```
{{name}}
```

yazıyoruz.

Kullandığımız Java Mustache uygulaması, değişken adıyla eşleşen parametresiz metotları ve `getName()` gibi getter’ları okuyabilir. Bu nedenle record’un `name()` erişim metodu da kullanılabilir. Şablona Java metot çağrısı yazmamız gerekmez. [GitHub](https://github.com/samskivert/jmustache?utm_source=chatgpt.com)

Tek bir isim için `Video` tipi oluşturmamızın faydası da burada belirginleşiyor: Veriyi **adı belli, tipi belli bir yapı** olarak temsil ediyoruz. Şablon, `name` özelliğini kullanabiliyor.

**Önce çalışan uygulamamızdaki tasarım ihtiyacını görelim.**

Şu anda `HomeController` üç işi bir arada yapıyor:

- `Video` veri tipini tanımlıyor.
- Video listesini kendi içinde tutuyor.
- HTTP isteğini karşılayıp veriyi şablona aktarıyor.

Küçük örneğimiz çalışıyor. Fakat yakında aynı videoları JSON olarak döndüren ikinci bir controller yazacağız.

O controller da video listesine ihtiyaç duyacak.

Listeyi ikinci controller’a da yazarsak aynı veriyi iki yerde yönetmeye başlayacağız. Verinin nasıl elde edildiğini değiştirmek istediğimizde birden fazla controller’ı düzenlememiz gerekecek.

Bu nedenle sorumlulukları şöyle ayıracağız:

| Parça            | Sorumluluğu                                                        |
| ---------------- | ------------------------------------------------------------------ |
| `Video`          | Bir videonun taşıdığı veriyi tanımlamak                            |
| `VideoService`   | Video verisini ve ilgili işlemleri yönetmek                        |
| `HomeController` | HTTP isteğini karşılamak, servisi kullanmak ve görünümü hazırlamak |

**Ekrandaki davranışı koruyup kodun iç yapısını düzenleyeceğiz.** Buna *refactoring* diyoruz.

Hedefimiz, controller’ın şu kadarını bilmesi:

> “Sayfada videoları göstereceğim. Video listesini `VideoService` üzerinden alabilirim.”

**İlk adım: `Video` tipini ayrı dosyaya taşıyalım.**

`HomeController` içindeki şu tanımı kaldır:

```
record Video(String name) {}
```

Aynı paket içinde **`Video.java`** dosyasını oluştur:

```
package com.learningspringboot4;

record Video(String name) {
}
```

Veri tipimizin içeriğini değiştirmedik. Artık ayrı bir dosyada duruyor.

Böylece hem `HomeController` hem `VideoService`, aynı `Video` tipini kullanabilecek.

**Burada neden `public` yazmadık?**

Java’da bu şekilde üst seviyede tanımlanmış bir tipe erişim belirleyicisi yazmazsak, erişimi **package-private** olur.

Bu, tipin aynı paketteki kod tarafından kullanılabildiği anlamına gelir.

Bizim üç dosyamız da şu pakette:

```
package com.learningspringboot4;
```

Bu nedenle birbirlerini kullanabilirler.

Şimdilik ayrı `controller`, `service` ve `model` paketleri oluşturmuyoruz. Böyle bir ayrım yaparsak `Video` tipinin erişimini de ona göre düzenlememiz gerekir. Java’da bir alt paket, erişim kuralları açısından üst paketle aynı paket sayılmaz.

Buradaki mühendislik alışkanlığı şu: **Bir tipi hangi kodun kullanması gerektiğini düşünerek görünürlüğünü belirlemek.**

**İkinci adım: `VideoService` sınıfını oluşturalım.**

Aynı paket içinde **`VideoService.java`** dosyasını oluştur:

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.stereotype.Service;

@Service
public class VideoService {

    private List<Video> videos = List.of(
        new Video("Need HELP with your SPRING BOOT 4 App?"),
        new Video("Don't do THIS to your own CODE!"),
        new Video("SECRETS to fix BROKEN CODE!")
    );

    public List<Video> getVideos() {
        return videos;
    }
}
```

Şimdi bu sınıfın yaptığı işi açalım.

**Liste artık servisin içinde tutuluyor.**

```
private List<Video> videos = List.of(...);
```

`videos`, `VideoService` nesnesinin bir alanı.

Başındaki **`private`**, diğer sınıfların bu alana doğrudan erişmesini sınırlar.

Controller’ın listeye ulaşması için şu metodu sunuyoruz:

```
public List<Video> getVideos() {
    return videos;
}
```

Bu metodu şöyle okuyabilirsin:

> “`getVideos()` çağrıldığında, eleman tipi `Video` olan bir liste döndür.”

Metot şu anda yalnızca mevcut listeyi veriyor. Daha sonra verinin elde edilme biçimini değiştirdiğimizde bu sorumluluğun sahibi servis olacak.

Bu, **encapsulation**, yani kapsülleme fikrinin küçük bir örneği: İçerideki alanı doğrudan açmak yerine, o veriyle nasıl etkileşim kurulacağını belirliyoruz.

Bir ayrıntı daha: `return videos`, burada listenin kopyasını üretmez. Mevcut listeye ait referansı döndürür. Önceki partta gördüğümüz gibi bu liste `List.of()` ile oluşturulduğu için eleman yapısı değiştirilemez.

**`@Service`, Spring’e sınıfın rolünü bildiriyor.**

```
@Service
```

Bu annotation, sınıfımızın servis rolünde bir Spring bileşeni olduğunu belirtir.

`@Service`, genel amaçlı `@Component` annotation’ının özelleştirilmiş biçimlerinden biridir. `@Controller` da bu ailede yer alır. Component scanning sırasında uygun paketlerdeki bu sınıflar bulunup bean tanımları kaydedilebilir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html?utm_source=chatgpt.com)

Burada iki şeyi birlikte yapıyoruz:

- Java ile bir sınıf ve onun davranışını tanımlıyoruz.
- Spring’e, bu sınıftan bir bileşeni yönetmesini sağlayacak bilgiyi veriyoruz.

**`@Service`, sınıfı ayrı bir sunucuya dönüştürmez.** Bu örnekte `VideoService`, aynı Java uygulaması içinde çalışan bir nesne olacak.

Controller ile servis arasındaki iletişim de normal Java metot çağrısıyla gerçekleşecek.

**Şimdi asıl soruya geldik: Controller bu servisi nasıl kullanacak?**

Bir nesnenin işini yapabilmek için başka bir nesneye ihtiyaç duymasına **bağımlılık** diyebiliriz.

Bizim örneğimizde:

> `HomeController`, video listesini almak için `VideoService` nesnesine ihtiyaç duyuyor.

Dolayısıyla `VideoService`, controller’ın bir bağımlılığı.

Controller’a önce şu alanı ekleyelim:

```
private final VideoService videoService;
```

Bu satırı acele etmeden okuyalım:

| Parça          | Görevi                                                             |
| -------------- | ------------------------------------------------------------------ |
| `private`      | Alanın dışarıdan doğrudan erişimini sınırlar                       |
| `final`        | İlk atamadan sonra alanın referansının yeniden atanmasını engeller |
| `VideoService` | Alanın tipi                                                        |
| `videoService` | Alanın adı                                                         |

Bu satır **yeni bir `VideoService` nesnesi oluşturmuyor**. Controller’ın bir servis referansı tutacağını belirtiyor.

Peki bu alanın değeri nereden gelecek?

**Constructor üzerinden alacağız.**

```
public HomeController(VideoService videoService) {
    this.videoService = videoService;
}
```

Bu, `HomeController` sınıfının **constructor’ı**.

Constructor, nesne oluşturulurken başlangıç durumunu hazırlayan yapıdır.

Burada tanıman gereken üç özellik var:

- Adı sınıfla aynıdır: `HomeController`.
- Bir dönüş tipi yazılmaz; `void` da yazılmaz.
- İhtiyaç duyduğu değerleri parametre olarak alabilir.

Bizim constructor’ımız şu parametreyi istiyor:

```
VideoService videoService
```

Yani:

> “Bir `HomeController` oluşturulurken bana bir `VideoService` referansı ver.”

**🔴 Şimdi `this.videoService = videoService;` satırını açalım.**

```
this.videoService = videoService;
```

Bu satırda aynı isimle görünen iki farklı yer var:

**Soldaki `this.videoService`:** Oluşturulmakta olan controller nesnesinin alanı.

**Sağdaki `videoService`:** Constructor’a verilen parametre.

`this`, burada **bu `HomeController` nesnesini** ifade eder.

Satırın anlamı:

> “Constructor’a verilen servis referansını, bu controller’ın alanına kaydet.”

Parametrenin adını değiştirirsek ilişki daha görünür olur:

```
public HomeController(VideoService gelenServis) {
    this.videoService = gelenServis;
}
```

İşlem aynı.

Burada servis nesnesi kopyalanmaz. Controller’ın alanına, verilen nesneye ait referans atanır.

Constructor tamamlandıktan sonra parametrenin kapsamı biter; fakat controller’ın alanındaki referans durur. Controller daha sonraki metot çağrılarında bu alanı kullanabilir.

**`final` konusunda önemli bir ayrım yapalım.**

```
private final VideoService videoService;
```

Bu alan, başlangıç atamasından sonra başka bir servis referansına atanamaz.

Fakat **`final`, servis nesnesinin içindeki bütün verileri değişmez yapmaz.**

Örneğin ileride `VideoService` içinde video ekleyen bir metot yazdığımızda controller o metodu çağırabilir. Servisin kendi verisinin değişmesiyle controller’ın başka bir servis nesnesine bağlanması farklı işlemlerdir.

Ayrıca `final`, tek başına `null` kontrolü yapmaz. Buradaki görevi, alanın yeniden atanmasını sınırlandırmaktır.

**Şimdi Java tarafındaki bağlantıyı Spring olmadan da görelim.**

Aşağıdaki iki satırı, yalnızca nesnelerin nasıl bağlandığını anlamak için düşün:

```
VideoService service = new VideoService();

HomeController controller = new HomeController(service);
```

İlk satır bir servis nesnesi oluşturur.

İkinci satır bir controller nesnesi oluştururken o servis referansını constructor’a verir.

Controller, constructor’a verilen referansı kendi alanına kaydeder.

**Dependency injection’ın temel fikri bu: Bir nesnenin ihtiyaç duyduğu nesneyi ona dışarıdan vermek.**

Bunu burada elle yaptık. Spring uygulamamızda ise bu bağlantıyı Spring kuracak.

Constructor aracılığıyla yaptığımız için bunun adı **constructor injection**.

Bu yaklaşım Java nesneleri arasında kurulabilir; Spring, bağımlılıkların bulunmasını ve bağlanmasını bizim için yönetir. Spring’in resmî dokümanı da zorunlu bağımlılıklar için constructor injection’ı önerir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html?utm_source=chatgpt.com)

**Spring bu iki nesneyi nasıl birbirine bağlayacak?**

Önce terimleri tek örnek üzerinde yerleştirelim.

**Bean**, Spring’in yönettiği nesnedir.

**Application context**, bean tanımlarını, nesnelerin oluşturulmasını ve aralarındaki bağımlılıkların çözülmesini yöneten Spring container’ıdır.

**Autowiring**, uygun bağımlılıkların Spring tarafından bulunup gerekli yerlere verilmesidir.

Bizim örneğimizde Spring şu bilgilerle çalışıyor:

```
@Service
public class VideoService {
    // ...
}
```

```
@Controller
public class HomeController {

    public HomeController(VideoService videoService) {
        // ...
    }
}
```

Uygulama başlarken, varsayılan düzenimizde süreç kabaca şöyle ilerler:

1. Spring, component scanning ile bu sınıfların bean tanımlarını bulur.
2. `HomeController` oluşturulurken constructor’ının `VideoService` istediği görülür.
3. Bu tipe uygun bean çözülür; gerekli servis nesnesi henüz oluşturulmadıysa oluşturulur.
4. Servis referansı, `HomeController` constructor’ına verilir.
5. Constructor içindeki Java kodumuz çalışır ve referans alana kaydedilir.

Burada “Önce bütün servisler, sonra bütün controller’lar oluşturulur” gibi bir kural ezberlemiyoruz. **Spring, ilgili nesneyi oluştururken onun bağımlılıklarını çözmek zorundadır.**

Bu örnekte tek bir `VideoService` bean’i bulunduğu için hangi nesnenin verileceği nettir.

Constructor parametresini `gelenServis` diye adlandırmamız da bunu değiştirmez. Bu basit örnekte Spring’in eşleştirdiği temel bilgi, istenen **`VideoService` tipi**.

**IoC ifadesini de burada yerine oturtabiliriz.**

*Inversion of Control*, kontrolün tersine çevrilmesi anlamına gelir.

Bu örnekte controller’ın bağımlılığını oluşturup bulma kontrolü, Spring container’ına bırakılıyor. Controller ise ihtiyacını constructor’ında bildiriyor.

**Dependency injection, bu kontrol düzenini gerçekleştirme yollarından biridir.**

Şu cümleyi kendi kelimelerinle kurabilmen yeterli:

> “Controller, çalışmak için neye ihtiyaç duyduğunu söylüyor. Spring uygun nesneyi sağlayarak controller’ı oluşturuyor.”

**Peki neden constructor’ın üzerinde `@Autowired` yok?**

Çünkü sınıfımızda **tek constructor** var.

Spring tarafından yönetilen bu sınıfın tek constructor’ı, ayrıca `@Autowired` yazılmadan kullanılabilir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html?utm_source=chatgpt.com)

Bu nedenle şu kullanım yeterli:

```
public HomeController(VideoService videoService) {
    this.videoService = videoService;
}
```

`@Autowired`, injection noktalarını belirtmek için constructor, setter metodu veya alan üzerinde kullanılabilir.

Bu farklılıkları şöyle ayıralım:

| Yapı                                                   | Görevi                                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `@Service`, `@Controller`, `@Component` gibi işaretler | Sınıfın Spring bileşeni olarak bulunmasına ve rolünün belirtilmesine yardımcı olur |
| Constructor parametresi                                | Nesnenin oluşturulurken ihtiyaç duyduğu bağımlılığı ifade eder                     |
| `@Autowired`                                           | Desteklenen injection noktalarını açıkça işaretleyebilir                           |
| Tek constructor                                        | Bu örnekte `@Autowired` yazılmadan kullanılabilir                                  |

`@RestController` ve `@Configuration` da component scanning ile bulunabilen Spring annotation’ları arasındadır; rollerini ilgili örneklerde kullanacağız.

Biz bu uygulamada **constructor injection** ile devam ediyoruz. Bağımlılığı sınıf oluşturulurken görünür kılması ve normal Java ile nesne oluşturmayı kolaylaştırması burada işimize yarıyor.

**`@Configuration` ve `@Bean` yaklaşımı da geçerli bir seçenek.**

Bir sınıfın üzerine `@Service` eklemek dışında, bir yapılandırma sınıfındaki `@Bean` metodu üzerinden de bean tanımlayabiliriz.

Bu yöntemde nesnenin oluşturulmasını metot içinde tarif ederiz; Spring de dönen nesneyi bean olarak yönetir. Özellikle oluşturulmasını özelleştirmek istediğimiz veya kaynak kodunu değiştiremediğimiz tiplerde yararlıdır. Bu yaklaşım güncel Spring’de de destekleniyor. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/beans/java/bean-annotation.html?utm_source=chatgpt.com)

Bizim `VideoService` sınıfımız için `@Service` ile tanımlama yeterli.

**Artık controller’ın tamamlanmış hâlini yazalım.**

`HomeController.java` dosyasında eski iç `Video` tanımını ve video listesini kaldırıyoruz. Dosyanın yeni hâli şu:

```

import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class HomeController {

    private final VideoService videoService;

    public HomeController(VideoService videoService) {
        this.videoService = videoService;
    }

    @GetMapping("/")
    public String index(Model model) {
        model.addAttribute("videos", videoService.getVideos());
        return "index";
    }
}
```

Şimdi isteği karşılayan metodu okuyalım:

```
@GetMapping("/")

    model.addAttribute("videos", videoService.getVideos());
    return "index";
}
```

Bu satırda:

```
model.addAttribute("videos", videoService.getVideos());
```

önce `videoService.getVideos()` çağrılır. Dönen liste, modele `"videos"` adıyla eklenir.

Aynı işlemi zihninde iki adım olarak düşünebilirsin:

```
List<Video> liste = videoService.getVideos();

Bu ikinci yazım yalnızca işlemi açarak göstermek için; ana kodumuzda tek satırlık sürümü kullanıyoruz.

1. Videoları servisten al.
2. Görünümün kullanacağı modele ekle.
3. `"index"` görünüm adını döndür.

| Kod                                         | Ne zaman kullanılıyor?                                     |
| ------------------------------------------- | ---------------------------------------------------------- |
| `HomeController(VideoService videoService)` | Controller nesnesi oluşturulurken bağımlılığını almak için |

**Her HTTP isteğinde yeniden servis mi oluşturuluyor?**

Mevcut varsayılan bean düzenimizde hayır.

Bu örnekte controller’a verilen servis referansı, sonraki çağrılarda da kullanılır. Şu nesneleri biz oluşturuyoruz:

```
new Video("Need HELP with your SPRING BOOT 4 App?")
```

Bunlar uygulamanın veri nesneleri.

`HomeController` ve `VideoService` ise bu örnekte Spring’in yönettiği bileşenler.

Spring kullanırken `new` yazmak ortadan kalkmaz. Önemli olan, **hangi nesnelerin yaşamını ve bağımlılıklarını Spring’in yönetmesini istediğimizi** bilmektir.

**Bu düzenlemeden sonra sayfayı yeniden kontrol edelim.**

Üç Java dosyamız aynı pakette olmalı:

- `Video.java`
- `VideoService.java`
- `HomeController.java`

Uygulamayı yeniden başlatıp ana sayfayı açtığında aynı üç videoyu görmeyi bekliyoruz. Bu kez listeye ulaşma işi servis üzerinden gerçekleşiyor.

Eğer Spring, `VideoService` bean’ini bulamadığını söylerse özellikle `@Service` annotation’ını ve sınıfın taranan paket içinde olup olmadığını kontrol et. Bu kurulumda zorunlu bağımlılık çözülemezse controller oluşturulamaz.

**Bugünün kısa tekrarı:**

- HTTP isteğinde controller, bu referans üzerinden `getVideos()` çağırdı.

2. **`final`, servisin içindeki verileri de değişmez yapar mı?** Hayır. Controller’daki servis referansının yeniden atanmasını engeller. Servisin kendi durumunun değişmesi ayrı bir konu.
3. **`@Service` kaldırılırsa constructor parametresi neden yeterli değil?** Constructor parametresi bir ihtiyacı bildirir. Bu ihtiyacı karşılayacak bean’in ayrıca tanımlanmış olması gerekir. Mevcut örneğimizde bunu `@Service` sağlıyor.

import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;

Bu metodu parçalara ayıralım.

```
@PostMapping("/new-video")
```

Şunu söylüyor:

> “`/new-video` yoluna gelen POST isteğini bu metotla karşıla.”

Tarayıcının adres çubuğuna `/new-video` yazmak aynı işlem değildir; adres çubuğundan normalde GET isteği gönderirsin. Buradaki metot için belirlediğimiz eşleşme **POST + `/new-video`**.

**🔴 Formdaki metin, `Video` nesnesine nasıl dönüşüyor?**

Metodun parametresine bakalım:

```
@ModelAttribute Video newVideo
```

`@ModelAttribute`, burada gelen istek parametrelerinin bir Java nesnesine bağlanmasını sağlıyor.

Bu işleme **data binding**, yani **veri bağlama** diyoruz.

Veri tipimiz şuydu:

```
record Video(String name) {}
```

Form alanımızın adı da:

```
name="name"
```

İsimler eşleşiyor:

**Formdaki `name` alanı**, `Video` nesnesinin **`name` bileşenine** karşılık geliyor.

Spring MVC, record’un constructor’ını kullanarak gelen değeri nesne oluşturulurken sağlayabilir. Constructor parametreleri üzerinden binding, Spring MVC tarafından desteklenir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/modelattrib-method-args.html?utm_source=chatgpt.com)

Sonuç bakımından şu nesnenin oluşturulduğunu düşünebilirsin:

```
new Video("Learning Spring Boot 4")
```

Bu nesnenin referansı, controller metodumuzdaki `newVideo` parametresine verilir.

Dolayısıyla metot çalışmaya başladığında:

```
newVideo.name()
```

ifadesi, gönderilen video adını okuyabilir.

Buradaki `Video`, o form gönderiminin verisini temsil eder. MVC’nin binding sırasında bu nesneyi oluşturması, onu application context’e bir servis bean’i olarak kaydettiği anlamına gelmez.

```
videoService.create(newVideo);
```

> “Bu video verisini al ve oluşturma işlemini gerçekleştir.”

`create()` metodunu birazdan yazacağız.

Son satırı da şimdilik şöyle okuyabilirsin:

**Şimdi servisin video eklemesini sağlayalım.**

`VideoService` içinde başlangıç listemiz şöyle oluşturuluyordu:

```
private List<Video> videos = List.of(
    new Video("Need HELP with your SPRING BOOT 4 App?"),
    new Video("Don't do THIS to your own CODE!"),
    new Video("SECRETS to fix BROKEN CODE!")
);
```

Yeni videoyu eklemek için ilk aklına şu gelebilir:

```
videos.add(newVideo);
```

Fakat önceki partta öğrendiğimiz bir özellik burada devreye giriyor:

**`List.of()` ile oluşturulan listenin eleman yapısı değiştirilemez.**

`List` arayüzünde `add()` metodu bulunduğu için bu çağrı derlenebilir. Ancak bu liste üzerinde çalıştırıldığında **`UnsupportedOperationException`** oluşur.

Buradan önemli bir Java dersi çıkıyor:

> **Bir metodun tip üzerinden kullanılabilir görünmesi, o nesnenin ilgili işlemi desteklediğini her durumda garanti etmez.**

Biz mevcut listeyi yerinde değiştirmek yerine, eski elemanları ve yeni videoyu içeren başka bir liste hazırlayacağız.

`VideoService` içine şu metodu ekle:

```
public Video create(Video newVideo) {
    List<Video> extend = new ArrayList<>(videos);
    extend.add(newVideo);
    this.videos = List.copyOf(extend);
    return newVideo;
}
```

Ayrıca şu import gerekiyor:

```
import java.util.ArrayList;
```

Şimdi dört satırın her birini anlayalım.

**Önce değiştirilebilir bir çalışma listesi oluşturuyoruz.**

```
List<Video> extend = new ArrayList<>(videos);
```

`ArrayList`, Java’nın `List` arayüzünü uygulayan somut liste sınıflarından biridir.

Burada kullandığımız constructor, mevcut `videos` listesindeki elemanlarla yeni bir `ArrayList` oluşturur. Eleman sırası korunur. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/ArrayList.html?utm_source=chatgpt.com)

Başlangıç listesinde üç video varsa, `extend` listesinde de başlangıçta o üç video bulunur.

`<>` işaretine **diamond operatörü** denir. Java, buradaki eleman tipinin `Video` olduğunu bağlamdan çıkarabilir. Bu yüzden sağ tarafta tekrar `ArrayList<Video>` yazmamız gerekmez.

Bir ayrıntıyı özellikle ayıralım:

**Yeni liste oluşturuluyor; içindeki her `Video` nesnesi yeniden oluşturulmuyor.**

Listeye, mevcut video nesnelerinin referansları aktarılıyor. Buna *shallow copy*, yani **sığ kopya** denir.

**Sonra yeni videoyu çalışma listesine ekliyoruz.**

```
extend.add(newVideo);
```

`extend` bir `ArrayList` olduğu için ekleme işlemini destekliyor.

Bu satırdan sonra çalışma listesinde dört eleman var.

Mevcut `videos` listesinin eleman yapısını hâlâ değiştirmedik.

**Ardından yeni bir değiştirilemeyen liste elde edip servis alanını güncelliyoruz.**

```
this.videos = List.copyOf(extend);
```

Burada iki işlem birlikte var.

Önce:

```
List.copyOf(extend)
```

`extend` listesinin elemanlarını içeren, değiştirilemeyen bir liste sağlar. Daha sonra kaynak `extend` listesinde yapılacak eleman ekleme veya çıkarma işlemleri bu sonucun eleman yapısına yansımaz. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html?utm_source=chatgpt.com)

Sonra:

```
this.videos = ...
```

Servisin `videos` alanını bu listeye yönlendirir.

🔴 **Eski listeyi değiştirmekle, alanın başka bir listeyi göstermesini sağlamak farklı işlemler.**

Bunu küçük bir tabloyla görelim:

| Aşama                               | Servisin `videos` alanındaki liste | Yerel `extend` listesi |
| ----------------------------------- | ---------------------------------- | ---------------------- |
| Başlangıç                           | A, B, C                            | Henüz yok              |
| `new ArrayList<>(videos)`           | A, B, C                            | A, B, C                |
| `extend.add(D)`                     | A, B, C                            | A, B, C, D             |
| `this.videos = List.copyOf(extend)` | A, B, C, D içeren yeni liste       | A, B, C, D             |

Eski listeye daha önce referans almış bir kod varsa, o eski listede hâlâ A, B, C bulunur. O listeye sonradan D eklemedik.

**Burada `final` bilgimizi de bağlayalım.**

Controller’daki alanımız:

```
private final VideoService videoService;
```

Servisteki alanımız:

```
private List<Video> videos;
```

Controller aynı servis nesnesine bağlı kalıyor. Servis ise kendi `videos` alanını yeni bir listeye atayabiliyor.

`videos` alanını `final` yapsaydık şu yeniden atamayı yapamazdık:

```
this.videos = List.copyOf(extend);
```

**Son satır, eklenen videoyu çağıran koda döndürüyor.**

```
return newVideo;
```

Metodun dönüş tipi `Video` olduğu için, eklediğimiz nesnenin referansını geri veriyoruz.

Controller şu anda bu dönüş değerini kullanmıyor:

```
videoService.create(newVideo);
```

Java’da bir metodun döndürdüğü değeri kullanmadan çağrı yapmak mümkündür. Burada controller için önemli olan, servisin listeyi güncellemiş olması.

Aynı servis metodunu JSON API tarafında kullanırken dönen değerden de yararlanacağız.

**Şimdi `redirect:/` satırının neden önemli olduğuna gelelim.**

Önceki partlarda:

```
return "index";
```

kullanıyorduk. Bu, görünümün adını belirtiyordu.

Şimdi:

```
return "redirect:/";
```

kullanıyoruz.

`redirect:` öneki, Spring MVC tarafından yönlendirme talimatı olarak yorumlanır. Varsayılan yönlendirme davranışında **302 Found** cevabı gönderilir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/view/RedirectView.html?utm_source=chatgpt.com)

Cevabın önemli kısmını sadeleştirelim:

```
HTTP/1.1 302 Found
Location: /
```

`Location`, tarayıcının hangi adrese yönlendirildiğini belirtir.

Normal tarayıcı form akışımızda, tarayıcı bu yönlendirmeyi izleyerek yeni bir istek gönderir:

```
GET /
```

Bu GET isteği, daha önce yazdığımız metodu çalıştırır:

```
@GetMapping("/")
public String index(Model model) {
    model.addAttribute("videos", videoService.getVideos());
    return "index";
}
```

Servisin listesi artık güncellenmiş durumda olduğu için yeni video da modele eklenir. Mustache bu listeyle HTML oluşturur.

**Yani `redirect:/`, `index()` metodunu doğrudan Java çağrısıyla çalıştırmıyor. Tarayıcıya yeni bir HTTP isteği yaptıran yönlendirme cevabını oluşturuyor.**

**Bu düzenin adı: Post/Redirect/Get.**

Üç aşama var:

1. **POST:** Form verisini gönder ve işlemi gerçekleştir.
2. **Redirect:** Tarayıcıyı sonuç sayfasına yönlendir.
3. **GET:** Sonuç sayfasını yeni bir istekle getir.

Bunun pratik faydası şu: Kullanıcı sonuç sayfasını yenilediğinde, normal akışta son GET isteği tekrarlanır. Video ekleyen POST isteğini tekrar göndermesi gerekmez.

Bu yaklaşım tek başına çift tıklama gibi bütün tekrar gönderimlerini engellemez; özellikle **işlem sonrasında sayfanın yenilenmesi** davranışını düzenler.

Yönlendirme kodlarını da karıştırmayalım:

| Kod                       | Temel anlamı                                            |
| ------------------------- | ------------------------------------------------------- |
| **301 Moved Permanently** | Kaynak kalıcı olarak başka adrese taşındı               |
| **302 Found**             | Geçici yönlendirme; mevcut örneğin varsayılan davranışı |
| **303 See Other**         | İşlemin sonucunu belirtilen kaynağı getirerek gör       |

HTTP standardı, 302 sonrasında istemcinin POST’u GET’e çevirmesine izin verir. 303 ise işlem sonucunu başka bir kaynaktan GET/HEAD ile alma anlamını daha açık ifade eder. Biz burada mevcut örneğin 302 akışını takip ediyoruz. [rfc-editor.org](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

**Controller’ın güncel hâli de şöyle:**

```

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;

@Controller
public class HomeController {

    private final VideoService videoService;

        this.videoService = videoService;
    }

    @GetMapping("/")

```

Bir controller içinde artık iki farklı HTTP davranışı var:

**GET `/`**, sayfayı oluşturuyor.  
**POST `/new-video`**, yeni veriyi işleyip yönlendirme yapıyor.

**🧠 Şimdi bu örneğin önemli sınırını doğru anlayalım.**

Yeni liste oluşturma yaklaşımı, daha önceki listenin eleman yapısını değiştirmememizi sağladı.

Fakat bu işlem **servisin durumunu değiştiriyor**:

```
this.videos = List.copyOf(extend);
```

Dolayısıyla “Kod artık hiçbir yan etkiye sahip değil” diyemeyiz. Servisin tuttuğu liste referansı güncelleniyor.

Ayrıca **değiştirilemeyen liste kullanmak, bu güncelleme işlemini kendiliğinden thread-safe yapmaz.**

*Thread-safe*, farklı iş parçacıkları aynı kodu eşzamanlı kullandığında beklenen doğruluğun korunması demektir.

Örneğin iki istek birbirine çok yakın gelsin:

- Birinci istek D videosunu eklemek istiyor.
- İkinci istek E videosunu eklemek istiyor.

Şu sıra mümkün:

| Adım | Birinci istek                       | İkinci istek                        |
| ---- | ----------------------------------- | ----------------------------------- |
| 1    | A, B, C listesini okur              | A, B, C listesini okur              |
| 2    | A, B, C, D listesini hazırlar       | A, B, C, E listesini hazırlar       |
| 3    | Servis alanını kendi listesine atar |                                     |
| 4    |                                     | Servis alanını kendi listesine atar |

Son durumda servis A, B, C, E listesini gösterir. D’nin eklenmesi kaybolmuştur.

Buna **lost update**, yani **kayıp güncelleme** denir. İşlemlerin birbirine denk gelme sırasına bağlı böyle problemlere *race condition* deriz.

Buradaki ders şu:

> **Tek tek liste nesnelerinin değiştirilememesi, “oku, kopyala, güncelle” adımlarının bir bütün olarak güvenli yürüdüğünü garanti etmez.**

Bu bölümde eşzamanlılık çözümünü büyütmeyeceğiz; fakat örneğimizin bu sınırını bilerek ilerleyeceğiz.

**Bir diğer ayrım: Verimiz şu anda bellekte.**

`create()` metodumuz veritabanına kayıt yapmıyor. Çalışan `VideoService` nesnesinin tuttuğu listeyi güncelliyor.

Bu yüzden:

- Sayfayı yenilediğinde, uygulama çalışmaya devam ettiği sürece güncel listeyi görürsün.
- Uygulamayı durdurup yeniden başlattığında başlangıçta tanımlanan üç video yeniden oluşturulur.
- Varsayılan tek servis nesnemizi kullanan istekler aynı listeyi paylaşır; bu örnekte kullanıcıya özel ayrı listeler oluşturmadık.

Bu aşamada video adının boş olmaması gibi iş kurallarını da henüz eklemedik. Şu an kurduğumuz mekanizma, **formdan veri alma ve bellekteki durumu güncelleme**.

Uygulamayı yeniden başlatıp ana sayfayı aç. Forma `Learning Spring Boot 4` yaz ve Submit’e bas.

Ana isteklerde şunları görmeyi bekliyoruz:

| İstek             | Beklenen cevap       |
| ----------------- | -------------------- |
| `POST /new-video` | `302` yönlendirmesi  |

**Bugünün kısa tekrarı:**

- HTML formu `name` alanını POST isteğiyle gönderdi.
- `@ModelAttribute`, gelen veriyi `Video` nesnesine bağladı.
- Controller, `create()` metoduyla işi servise devretti.
- Servis değiştirilebilir bir çalışma listesi hazırlayıp yeni videoyu ekledi.
- `List.copyOf()` sonucunu `videos` alanına atadı.
- Yönlendirme sonrasında yapılan GET, güncel listeyi gösterdi.

✍️ **Küçük uygulaman:** Bir video ekle, ardından sonuç sayfasını iki kez yenile. Network panelinden yenilemelerin hangi HTTP metoduyla yapıldığını izle. Son olarak uygulamayı yeniden başlatıp eklediğin videonun neden kaybolduğunu açıklamaya çalış.

Üç kontrol sorumuz:

1. Formdaki `name="name"` ile `record Video(String name)` arasındaki bağlantı nedir? `@ModelAttribute` bu süreçte ne yapıyor?
2. `return "index"` ile `return "redirect:/"` arasındaki fark nedir? Hangisinde tarayıcı yeni bir istek gönderiyor?
3. `new ArrayList<>(videos)`, `extend.add(newVideo)` ve `this.videos = List.copyOf(extend)` satırları hangi nesneleri oluşturuyor veya değiştiriyor? Eski listenin eleman yapısı değişiyor mu?

Fırat, bugün uygulamamıza iki yeni yetenek kazandırıyoruz: **Videoları JSON olarak listelemek ve JSON göndererek yeni video eklemek.**

Burada özellikle şunu anlamanı istiyorum: İsteğin içindeki veri nasıl Java nesnesine dönüşüyor, bizim kodumuz nerede çalışıyor ve sonuç nasıl HTTP cevabına dönüşüyor?

*Bu part, 001.pdf içindeki 43–48. sayfaların “Creating JSON-based APIs” bölümünü kapsıyor.*

---

**Önce Part 4’teki üç noktayı yerine oturtalım.**

**1. Formdaki `name="name"` ne işe yarıyordu?**

Tarayıcı, input’a yazdığın değeri `name` isimli bir form alanı olarak gönderiyordu. Spring MVC, `@ModelAttribute` sayesinde bu alanı `Video` record’undaki `name` bileşeniyle eşleştirerek bir `Video` nesnesi oluşturuyordu.

**2. `"index"` ile `"redirect:/"` arasındaki fark neydi?**

Önceki `@Controller` yapımızda:

- `"index"`: Sunucuda `index.mustache` şablonunun render edilmesini sağlıyordu.
- `"redirect:/"`: Tarayıcıya `/` adresine gitmesini söylüyordu. Ardından tarayıcı yeni bir GET isteği gönderiyordu.

**3. Listeyi güncellerken ne yapıyorduk?**

`new ArrayList<>(videos)` ile mevcut eleman referanslarını yeni, değiştirilebilir bir listeye alıyorduk. Yeni videoyu bu listeye ekleyip `List.copyOf(extend)` sonucunu `videos` alanına atıyorduk.

Eski listenin yapısı değişmiyordu; `videos` artık güncellenmiş başka bir listeyi gösteriyordu.

Bugün aynı `VideoService` üzerinden devam ediyoruz.

---

**1. HTML sayfasının yanına neden JSON API ekliyoruz?**

Şu anda bir kullanıcı `/` adresine geldiğinde, videoları HTML sayfasının içinde görüyor.

Bir React uygulaması düşün. Videoları kendi bileşenleriyle ekrana yerleştirmek istiyor. Backend’den alacağı veri şöyle olabilir:

```
[
  {"name": "Birinci video"},
  {"name": "İkinci video"}
]
```

React bu veriyi kullanarak kendi arayüzünü oluşturabilir. Aynı veriyi bir mobil uygulama da kullanabilir.

Böylece uygulamamızda iki sunum biçimi olacak:

| İstek             | İstemciye gönderilen               |
| ----------------- | ---------------------------------- |
| `GET /`           | Videoların yer aldığı HTML sayfası |
| `GET /api/videos` | Videoları içeren JSON verisi       |

İkisi de aynı video verisine ulaşacak.

Burada **API**, başka programların uygulamamızla nasıl etkileşime geçebileceğini belirleyen arayüzdür. Biz bu arayüzü HTTP adresleri, metotları ve veri biçimleriyle oluşturuyoruz.

Örneğin:

> “Videoları listelemek istiyorsan `/api/videos` adresine GET isteği gönder.”

Bu, API’mizin sunduğu işlemlerden biri.

**2. Java nesnesiyle JSON arasındaki dönüşümü Jackson yapıyor.**

Java tarafında şunu oluşturabiliyoruz:

```
new Video("Learning Spring Boot 4")
```

Bu, uygulamanın belleğinde bulunan bir Java nesnesidir.

HTTP üzerinden gönderebileceğimiz JSON karşılığı ise şöyle:

```
{
  "name": "Learning Spring Boot 4"
}
```

Bu iki biçim arasındaki dönüşümlerin isimlerini öğrenelim:

| Yön                                     | İşlemin adı                          |
| --------------------------------------- | ------------------------------------ |
| Java nesnesinden JSON üretmek           | **Serialization — serileştirme**     |
| JSON verisinden Java nesnesi oluşturmak | **Deserialization — deserileştirme** |

**Jackson**, bu dönüşümleri yapabilen kütüphanedir.

Projemizi oluştururken eklediğimiz web starter’ı gerekli JSON desteğini getiriyor. Spring Boot da uygun yapılandırmayı hazırlıyor. Spring MVC, HTTP gövdelerini okuyup yazarken **`HttpMessageConverter`** adlı dönüştürücü mekanizmasını kullanıyor; bizim JSON işlemlerimizde Jackson bu mekanizmanın içinde çalışıyor. [docs.spring.io](https://docs.spring.io/spring-boot/reference/web/servlet.html?utm_source=chatgpt.com)

Şimdilik bu teknik ismi ezberlemene gerek yok. Görev paylaşımını bilmen yeterli:

- **Bizim kodumuz:** `Video` ve `List<Video>` gibi Java nesneleriyle çalışır.
- **Spring MVC:** İstekleri ilgili metotlara ulaştırır ve HTTP cevabını oluşturma sürecini yönetir.
- **Jackson:** Java nesneleriyle JSON arasındaki dönüşümü gerçekleştirir.

İstemciye Java nesnesinin bellek referansı gönderilmez. Nesnenin verisini temsil eden JSON gönderilir.

**3. `@RestController` ile API controller’ımızı oluşturalım.**

Diğer sınıflarımızla aynı `com.learningspringboot4` paketinde **`ApiController.java`** oluştur:

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ApiController {

    private final VideoService videoService;

    public ApiController(VideoService videoService) {
        this.videoService = videoService;
    }

    @GetMapping("/api/videos")
    public List<Video> all() {
        return videoService.getVideos();
    }
}
```

Constructor ve `private final` kısmını artık tanıyoruz. Spring, controller’ı oluştururken ihtiyaç duyduğu `VideoService` bağımlılığını constructor üzerinden sağlıyor.

**Burada `VideoService` kopyalanmıyor.** Mevcut yapılandırmamızda `HomeController` ve `ApiController`, Spring’in yönettiği **aynı `VideoService` nesnesinin referansını** alıyor.

Yeni kavramımız `@RestController`.

Bu annotation, controller’ın component scanning ile bulunmasını sağlar. Ayrıca web metotlarının döndürdüğü değerlerin **HTTP response body’ye**, yani cevap gövdesine yazılmasını sağlar.

Davranış bakımından iki annotation’ı bir araya getirir:

```
@Controller
@ResponseBody
```

`@RestController`, bu ikisinin birleşimini sunar. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html?utm_source=chatgpt.com)

Önceki controller’ımızda:

```
return "index";
```

dediğimizde `"index"` bir **view adı** olarak yorumlanıyordu.

Burada ise:

```
return videoService.getVideos();
```

dediğimizde dönen liste, **cevap gövdesine yazılacak veri** olarak ele alınıyor.

🔴 **Önemli ayrım:** `@RestController` tek başına “her sonuç mutlaka JSON olur” anlamına gelmez. Sonucun nasıl yazılacağı, dönüş tipine ve kullanılabilen dönüştürücülere bağlıdır. Bizim `List<Video>` sonucumuz, mevcut JSON desteğiyle JSON olarak gönderiliyor.

**4. İlk endpoint’imizin her parçasını okuyalım.**

```
@GetMapping("/api/videos")
public List<Video> all() {
    return videoService.getVideos();
}
```

**`@GetMapping("/api/videos")`**

Şu isteği bu metoda bağlar:

```
GET /api/videos
```

Burada belirleyici olan, HTTP metodu ve adrestir.

Java metodunun adını `all()` yerine `listVideos()` yapsaydık, annotation aynı kaldığı sürece dışarıdaki adres değişmezdi.

**`public List<Video> all()`**

Metodumuz, elemanları `Video` olan bir liste döndürüyor.

Dönüş tipi `String` değil. Metodun içinde elle JSON metni üretmiyoruz.

**`return videoService.getVideos();`**

Önce servis metodunu çağırıyoruz. Aldığımız listeyi de `all()` metodunun sonucu olarak döndürüyoruz.

Bundan sonra Spring MVC’nin cevap yazma mekanizması devreye giriyor ve Jackson listeyi JSON’a dönüştürüyor.

Uygulama çalışırken terminalde:

```
curl http://localhost:8080/api/videos
```

komutunu çalıştırabilirsin. `curl`, terminalden HTTP istekleri göndermemizi sağlayan bir araçtır.

Uygulamayı yeni başlattıysan ve henüz video eklemediysen, beklenen veri şöyle:

```
[
  {
    "name": "Need HELP with your SPRING BOOT 4 App?"
  },
  {
    "name": "Don't do THIS to your own CODE!"
  },
  {
    "name": "SECRETS to fix BROKEN CODE!"
  }
]
```

Çıktı terminalinde tek satır görünebilir; burada okunabilirlik için düzenledim.

Bu yapıda:

- Dıştaki `[...]`, JSON dizisidir.
- İçindeki her `{...}`, bir videoyu temsil eden JSON nesnesidir.
- `"name"`, `Video` record’umuzdaki veriyi temsil eder.

Bir ayrıntıyı özellikle fark et: Mustache için daha önce `model.addAttribute("videos", ...)` kullanıyorduk. Burada `Model` kullanmadık; doğrudan liste döndürdük. Bu nedenle JSON’un dışına otomatik olarak `"videos"` isimli bir alan eklenmiyor.

**5. HTTP metotlarının anlamını doğru öğrenelim.**

Birazdan veri eklemek için POST kullanacağız. Önce dört temel metodun niyetini ayıralım:

| Metot      | Temel kullanım                                                   | Safe? | Idempotent?   |
| ---------- | ---------------------------------------------------------------- | ----- | ------------- |
| **GET**    | Veriyi okumak                                                    | Evet  | Evet          |
| **POST**   | Gönderilen veriyi işlemek; örneğin yeni kayıt eklemek            | Hayır | Garanti değil |
| **PUT**    | Belirli bir kaynağı verilen içerikle oluşturmak veya değiştirmek | Hayır | Evet          |
| **DELETE** | Belirli bir kaynağı kaldırmak                                    | Hayır | Evet          |

**Safe**, isteğin amacının sunucudaki uygulama verisini değiştirmek olmaması demektir. GET sırasında erişim kaydı tutulabilir; bu, onu otomatik olarak unsafe yapmaz.

**Idempotent**, aynı isteğin tekrar uygulanmasının hedeflenen etkisinin, bir kez uygulanmasıyla aynı olması demektir. **Cevabın her seferinde aynı olması şart değildir.** [rfc-editor.org](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

Bunu uygulamamız üzerinden düşün:

**Videoları iki kez listelemek**

İki GET isteği gönderdin. Listeye yeni video eklemedin. Okuma işlemini tekrar etmiş oldun.

Arada başka biri video eklerse ikinci GET’in cevabı değişebilir. Bu, GET’in idempotent olmasına aykırı değildir.

**Aynı videoyu iki kez eklemek**

Mevcut `create()` metodumuz her çağrıda listeye bir eleman ekliyor.

Aynı içerikle iki POST gönderirsen aynı isimde iki kayıt oluşur. Bir kez göndermekle iki kez göndermek aynı etkiyi yaratmaz.

**Belirli bir kaydı silmek**

İlk istekten sonra kayıt yoktur. Tekrar silme isteğinden sonra da yoktur. Sunucunun ikinci isteğe verdiği cevap farklı olabilir; hedeflenen son durum aynıdır.

Küçük bir mühendislik notu: POST’un kullanımı kayıt eklemekten daha geniştir. Ayrıca bu metot adları, Java kodumuzu kendiliğinden doğru davranmaya zorlamaz. Bir GET metodunun içine veri silen kod yazarsak, HTTP’nin beklenen anlamını biz ihlal etmiş oluruz.

**6. Şimdi JSON kabul ederek video ekleyelim.**

`ApiController` dosyanın import bölümüne şunları ekle:

```
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
```

Ardından sınıfın içine, `all()` metodunun altına şu metodu ekle:

```
@PostMapping("/api/videos")
public Video newVideo(@RequestBody Video newVideo) {
    return videoService.create(newVideo);
}
```

Aynı adreste artık iki işlemimiz var:

| İstek              | Çalışacak Java metodu |
| ------------------ | --------------------- |
| `GET /api/videos`  | `all()`               |
| `POST /api/videos` | `newVideo(...)`       |

Adresleri aynı olsa da HTTP metotları farklı olduğu için Spring bunları ayırt edebiliyor.

Şimdi yeni satırın üzerine odaklanalım:

```
@RequestBody Video newVideo
```

Bunun anlamı:

> “HTTP isteğinin gövdesini oku ve bu parametre için bir `Video` nesnesine dönüştür.”

JSON gönderdiğimiz bu akışta Spring MVC, uygun dönüştürücü üzerinden Jackson’ı kullanır. Metodumuz çalışmaya başladığında `newVideo` parametresinde artık bir Java `Video` nesnesi bulunur. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestbody.html?utm_source=chatgpt.com)

Gönderdiğimiz veri:

```
{
  "name": "Learning Spring Boot 4"
}
```

Hedef Java tipimiz:

```
record Video(String name) {}
```

Jackson, JSON’daki `name` değerini kullanarak bu record’dan bir nesne oluşturur.

Burada JSON alanının adı `newVideo` olmak zorunda değildir. **`newVideo`, Java metodundaki parametrenin adıdır; `"name"` ise taşıdığımız verinin alanıdır.**

Son satırımız:

```
return videoService.create(newVideo);
```

İki işi ardışık yapıyor:

1. Servis metodunu çağırarak videoyu listeye ekliyor.
2. Servisten dönen `Video` nesnesini controller metodunun sonucu olarak döndürüyor.

Aynı ifadeyi öğrenmek amacıyla açarsak:

```
Video createdVideo = videoService.create(newVideo);
return createdVideo;
```

Bu iki yazım aynı işi yapar.

Part 4’te HTML controller’ımız, `create()` metodunun döndürdüğü değeri kullanmıyordu. Burada ise bu değeri istemciye gönderilecek cevap için kullanıyoruz.

**7. `@ModelAttribute` ve `@RequestBody` farkını burada netleştirelim.**

İki akışımız da video ekliyor; fakat gelen verinin biçimi ve onu okuma yöntemi farklı:

| Ayrıntı                         | HTML formumuz                                 | JSON API’miz                          |
| ------------------------------- | --------------------------------------------- | ------------------------------------- |
| İstek                           | `POST /new-video`                             | `POST /api/videos`                    |
| İstek gövdesi                   | `name=Learning+Spring+Boot+4`                 | `{"name":"Learning Spring Boot 4"}`   |
| İstek `Content-Type` değeri     | `application/x-www-form-urlencoded`           | `application/json`                    |
| Parametreyi hazırlayan yaklaşım | `@ModelAttribute` ile form alanlarını bağlama | `@RequestBody` ile gövdeyi dönüştürme |
| Controller’ın sonucu            | `"redirect:/"`                                | Eklenen `Video`                       |
| İstemciye cevap                 | Yönlendirme                                   | JSON veri                             |

**POST, gönderilen verinin JSON olduğunu söylemez.** İki örnekte de POST kullanıyoruz; gövde biçimleri farklı.

Bir başka önemli ayrım:

- **`@RequestBody`**, gelen isteğin gövdesiyle ilgilidir.
- **`@RestController` içindeki `@ResponseBody` davranışı**, giden cevabın gövdesiyle ilgilidir.

Dolayısıyla `@RestController` kullandık diye JSON parametremizdeki `@RequestBody` gereksiz hâle gelmez.

Ayrıca JSON’un Java nesnesine dönüştürülebilmesi, verinin bütün iş kurallarımıza uygun olduğunu göstermez. Örneğin video adının boş olmaması gibi bir kuralı henüz tanımlamadık.

**9. `curl` ile video ekleyelim ve cevabı okuyalım.**

Uygulaman çalışırken aşağıdaki komutu kullanabilirsin. Bu çok satırlı yazım Bash/Zsh içindir; satır sonundaki `\`, komutun sonraki satırda devam ettiğini belirtir.

```
curl -v -X POST http://localhost:8080/api/videos \
  -d '{"name": "Learning Spring Boot 4"}' \
  -H 'Content-Type: application/json'
```

Komutun her parçasının bir görevi var:

| Parça                                 | Görevi                                           |
| ------------------------------------- | ------------------------------------------------ |
| `curl`                                | HTTP isteğini gönderen program                   |
| `-v`                                  | İstek ve cevap hakkında ayrıntılı çıktı gösterir |
| `-X POST`                             | Kullanılacak HTTP metodunu belirtir              |
| `http://localhost:8080/api/videos`    | İsteğin hedef adresi                             |
| `-d '...'`                            | Gönderilecek gövdeyi verir                       |
| `-H 'Content-Type: application/json'` | Gövdenin JSON biçiminde olduğunu belirtir        |

Dıştaki tek tırnaklar terminalin JSON metnini tek argüman olarak ele alması içindir. JSON’un kendi alan ve metin değerlerinde çift tırnak kullanıyoruz.

Küçük bir ayrıntı: `-d` zaten varsayılan olarak POST kullanımını sağlar. Burada `-X POST`, metodu açıkça görmek için yazılı. [How To Use](https://curl.se/docs/manpage.html?utm_source=chatgpt.com)

**`Content-Type` özellikle önemli.** Gövdeye JSON yazmakla, sunucuya gövdenin JSON olduğunu bildirmek birbirini tamamlayan iki adımdır.

Çıktının ilgili bölümleri aşağıdakine benzer. Sürüm bilgisi ve ek başlıklar sende farklı olabilir:

```
> POST /api/videos HTTP/1.1
> Host: localhost:8080
> User-Agent: curl/8.7.1
> Accept: */*
> Content-Type: application/json
> Content-Length: 34
>
< HTTP/1.1 200
< Content-Type: application/json
<
{"name":"Learning Spring Boot 4"}
```

Çıktıyı okurken:

- `>` işaretli satırlar, gönderilen isteğin bilgilerini gösterir.
- `<` işaretli satırlar, gelen cevabın bilgilerini gösterir.
- En alttaki JSON, cevap gövdesidir.

Başlıkları da anlayalım:

| Başlık                   | Bu örnekte anlamı                                         |
| ------------------------ | --------------------------------------------------------- |
| `Host`                   | Hedef sunucu ve port                                      |
| `User-Agent`             | İsteği gönderen programın bilgisi                         |
| `Accept: */*`            | İstemcinin her medya türünü kabul edebildiğini belirtmesi |
| İstekteki `Content-Type` | Gönderdiğimiz gövdenin biçimi                             |
| `Content-Length`         | Gövdenin bayt cinsinden uzunluğu                          |
| Cevaptaki `Content-Type` | Sunucudan gelen gövdenin biçimi                           |

`Content-Length` değerini elle yazmıyoruz; curl hesaplıyor.

**Peki neden `200`, neden `201` değil?**

Bu controller’da özel bir cevap durumu belirlemedik; başarılı işlemimiz `200` dönüyor.

Yeni kaynak oluşturulduğunu daha açık ifade eden durum kodu **`201 Created`**’dır. Gerçek bir oluşturma endpoint’i tasarlarken bunu değerlendireceğiz. Ancak `@PostMapping` yazmak, Spring’in kendiliğinden `201` göndermesini sağlamaz. [rfc-editor.org](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

Eklenen kaydın JSON’unu cevapta döndürmek de bizim API tercihimizdir. Her veri değiştirme işleminin mutlaka kaydın kendisini döndürmesi gerekmez.

**2. Maven’e frontend hazırlama adımlarını ekleyelim.**

Java tarafında bağımlılıklarımızı `pom.xml` üzerinden yönetiyorduk. Şimdi aynı dosyada, Maven’in frontend araçlarını da çalıştırmasını sağlayacağız.

Bunun için **`frontend-maven-plugin`** kullanıyoruz.

`pom.xml` içindeki `<build>` → `<plugins>` bölümüne, mevcut Spring Boot plugin’inin yanına aşağıdaki plugin’i ekle:

<plugin>

        <nodeVersion>v24.21.0</nodeVersion>

    <executions>
        <execution>
            <id>install-node-and-npm</id>
            <phase>generate-resources</phase>
            <goals>

            </goals>
        </execution>

        <execution>
            <id>npm-install</id>
            <phase>generate-resources</phase>
            <goals>
                <goal>npm</goal>
            </goals>
            <configuration>
                <arguments>install</arguments>
            </configuration>
        </execution>

        <execution>
            <id>parcel-build</id>
            <phase>generate-resources</phase>
            <goals>
                <goal>npx</goal>
            </goals>
            <configuration>
                <arguments>parcel build</arguments>
            </configuration>
        </execution>
    </executions>
</plugin>
```

Burada bölüm boyunca kurulacak üç adımı birlikte gösterdim:

1. Node.js ve npm’i hazırla.

**3. npm ve Parcel için proje tanımımızı hazırlayalım.**

Java tarafındaki `pom.xml` gibi, JavaScript paketlerinin de bir proje tanım dosyası var: **`package.json`**.

Proje kökünde, `pom.xml` ile aynı seviyede başlangıç içeriği şöyle olan bir `package.json` oluştur:

```
{
  "private": true,
  "source": "src/main/javascript/index.js",
  "targets": {
    "default": {
      "context": "browser",
      "outputFormat": "esmodule",
      "distDir": "target/classes/static"
    }
  }
}
```

Buradaki alanları okuyalım:

| Alan                       | Anlamı                                                          |
| -------------------------- | --------------------------------------------------------------- |
| `private`                  | Bu projenin yanlışlıkla npm paketi olarak yayımlanmasını önler. |
| `source`                   | Parcel’in işlemeye başlayacağı giriş dosyası.                   |
| `targets`                  | Üretilecek çıktıların ayarları.                                 |
| `default`                  | Bu örnekte kullandığımız çıktı hedefinin adı.                   |
| `context: "browser"`       | Çıktının tarayıcı için hazırlandığını belirtir.                 |
| `outputFormat: "esmodule"` | JavaScript modülü biçiminde çıktı üretir.                       |
| `distDir`                  | Üretilen dosyaların yazılacağı klasör.                          |

`context` ve `outputFormat` alanlarını, hedef ortamı ve modül biçimini açıkça belirtmek için ekledim. Parcel’in ES module çıktısı, birazdan kullanacağımız `<script type="module">` ile yüklenebilir. [parceljs.org](https://parceljs.org/features/targets/?utm_source=chatgpt.com)

Şimdi Parcel’i yükleyelim:

```
./mvnw frontend:npm "-Dfrontend.npm.arguments=install --save-dev parcel"
```

Bu komut, plugin’in kurduğu npm üzerinden şu işlemi yaptırır:

```
npm install --save-dev parcel
```

PDF’teki `node/npm ...` çağrısıyla aynı paket kurma amacını taşıyor; burada yerel npm’i plugin üzerinden çağırıyoruz.

**`--save-dev` ne söylüyor?**

Parcel, kaynak kodumuzu hazırlarken kullandığımız bir geliştirme aracıdır. Bu nedenle `package.json` içindeki **`devDependencies`** bölümüne eklenir.

Birazdan React’i kurduğumuzda ise React kodu, tarayıcıya gönderilecek uygulama çıktısının parçası olacak.

npm kurulumu sırasında şunları göreceksin:

- `node_modules`: İndirilen JavaScript paketleri.
- `package-lock.json`: Çözümlenen bağımlılık sürümlerinin kaydı.
- `package.json`: Bağımlılık bilgilerinin eklendiği proje tanımı.

`node` ve `node_modules` klasörlerini `.gitignore` içine ekleriz. Üretilen `target` klasörü ve Parcel önbelleği de sürüm kontrolüne alınmaz. **`package.json` ile `package-lock.json` ise projeyle birlikte saklanır.**

🔴 **İki komutu karıştırmayalım:**

- `npm install`, bağımlılıkları kurar.
- Bu projede asıl bundle üretimini `npx parcel build` yapar.

Maven yapılandırmamızdaki ikinci ve üçüncü görevlerin ayrı olmasının nedeni bu.

**4. `src` ile `target` klasörlerinin farkı burada çok önemli.**

Şu iki konumu yan yana düşün:

```
src/main/javascript/index.js
```

```
target/classes/static/index.js
```

İlk dosya, bizim yazdığımız **kaynak kod**.

İkinci dosya ise Parcel’in ürettiği **build çıktısı**.

Üretilen dosyayı elle düzenlersen, sonraki build sırasında değişikliğin kaybolabilir. Değişikliği kaynak dosyada yapar, çıktıyı yeniden üretiriz.

Spring Boot, classpath üzerindeki `static` dizininde bulunan dosyaları HTTP üzerinden sunabilir. Maven projesinde `target/classes`, çalıştırmada kullanılan classpath’in temel dizinlerinden biridir. [docs.spring.io](https://docs.spring.io/spring-boot/reference/web/servlet.html?utm_source=chatgpt.com)

Bu yüzden eşleşme şöyle olur:

| Projedeki konum                               | Kullanımı                                                              |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| `src/main/javascript/index.js`                | Parcel’in okuyacağı kaynak dosya                                       |
| `target/classes/static/index.js`              | Tarayıcıya `/index.js` adresinden sunulacak çıktı                      |
| `src/main/resources/static/style.css`         | Elle yazılmış statik kaynak; build sırasında çıktı dizinine kopyalanır |
| `src/main/resources/templates/react.mustache` | Controller üzerinden render edilecek şablon                            |

**URL içinde `target/classes/static` yazmıyoruz.** Tarayıcı bizim proje klasör yapımızı bilmek zorunda değil.

Ayrıca `mvn clean`, `target` altındaki çıktıları temizler. Kaynak dosyalarımız durduğu için sonraki build’de bunları yeniden üretebiliriz.

**DOM**, tarayıcının HTML belgesini bellekte temsil ettiği yapıdır. Ekrandaki başlık, liste ve input gibi elemanlar bu yapının parçalarıdır.

import React from "react";

Bu dosyayı satır satır anlamlandıralım:

**`document.getElementById("app")`**, HTML içinde `id="app"` olan elemanı bulur.

**`if (container)`**, eleman bulunduysa devam etmemizi sağlar.

**`createRoot(container)`**, React’in bu elemanın içini yönetmesini sağlayacak kökü oluşturur.

**`root.render(<App />)`**, ana bileşenimizi bu kökte gösterir.

Birazdan HTML sayfamıza şu elemanı koyacağız:

**7. Backend’den videoları alıp listeleyelim.**

**`ListOfVideos.js`** dosyasını oluştur:

```
import React from "react";

class ListOfVideos extends React.Component {

    constructor(props) {
        super(props);
        this.state = { data: [] };
    }

    async componentDidMount() {
        try {
            const response = await fetch("/api/videos");

            if (!response.ok) {
                throw new Error(`HTTP ${response.status}`);
            }

            const json = await response.json();

            this.setState({ data: json });
        } catch (error) {
            console.error("Videolar alınamadı.", error);
        }
    }

    render() {
        return (
            <ul>
                {this.state.data.map((item, index) => (
                    <li key={index}>
                        {item.name}
                    </li>
                ))}
            </ul>
        );
    }
}

export default ListOfVideos;
```

Bu dosya daha kalabalık görünüyor. Dört parçaya ayıralım.

**İlk parça: Bileşenin başlangıç durumu**

```
constructor(props) {
    super(props);
    this.state = { data: [] };
}
```

`extends React.Component`, bu JavaScript sınıfının React’in bileşen sınıfını genişlettiğini belirtir.

`super(props)`, üst sınıfın constructor’ını çağırır.

`this.state`, bileşenin kendi durumunu tutar. Başlangıçta:

```
{ data: [] }
```

diyoruz. Henüz backend’den veri gelmediği için boş bir dizimiz var.

**İkinci parça: Bileşen ekrana yerleşince veri almak**

```
async componentDidMount() {
    // ...
}
```

`componentDidMount`, bileşen ekrana yerleştirildikten sonra React tarafından çağrılır. Burada API isteğimizi başlatıyoruz.

```
const response = await fetch("/api/videos");
const json = await response.json();
```

🔴 **Bu iki satır, bölümün en önemli noktalarından biri.**

`fetch()`, doğrudan video dizisini döndürmez. Sonradan HTTP cevabına ulaşacağımız bir **Promise** döndürür.

İlk `await` sonucunda bir **`Response` nesnesi** elde ederiz. Bu nesnede cevap durumu, başlıklar ve gövdeye erişme yöntemleri bulunur.

`response.json()` ise cevap gövdesini okuyup JSON’u JavaScript değerlerine dönüştürür. Bu işlem de asenkron olduğu için ikinci kez `await` kullanırız. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch?utm_source=chatgpt.com)

PDF’teki şu ifadeyi bu nedenle düzeltiyoruz:

```
await fetch("/api/videos").json()
```

Bu yazımda `.json()`, HTTP cevabı elde edilmeden `fetch()` çağrısının döndürdüğü Promise üzerinde çağrılmaya çalışılır.

**Üçüncü parça: Gelen veriyi state’e koymak**

```
this.setState({ data: json });
```

Artık `json` değişkeninde JSON metni değil, JavaScript dizisi ve nesneleri var.

Bu veriyi state’e koyuyoruz. `setState`, React’e yeni durumla arayüzü güncellemesi gerektiğini bildirir; güncellemeyi sıraya alır. Hemen sonraki satırda state’in değişmiş olduğunu varsaymayız. [React](https://react.dev/reference/react/Component?utm_source=chatgpt.com)

**Dördüncü parça: Diziden liste elemanları üretmek**

```
this.state.data.map((item, index) => (
    <li key={index}>
        {item.name}
    </li>
))
```

`map`, dizinin her elemanı için bir sonuç üretir. Burada her video için bir `<li>` oluşturuyoruz.

`item.name`, o JavaScript nesnesindeki video adıdır.

Dizi boşsa üretilecek liste elemanı da yoktur.

`key`, React’in liste elemanlarını ayırt etmesine yardımcı olur. Modelimizde henüz bir video kimliği bulunmadığı için, bu basit ve yeniden yüklenen listede geçici olarak `index` kullandım. Sırası değişen, silinen veya araya eleman eklenen gerçek listelerde kararlı bir kayıt kimliği tercih edilir. [React](https://react.dev/learn/rendering-lists?utm_source=chatgpt.com)

**8. Frontend state’i ile backend verisi aynı yerde yaşamıyor.**

Şu iki veriyi ayırmanı istiyorum:

| Veri                                      | Nerede bulunuyor?                        |
| ----------------------------------------- | ---------------------------------------- |
| `VideoService` içindeki `videos`          | Sunucudaki Java uygulamasının belleğinde |
| `ListOfVideos` içindeki `this.state.data` | Kullanıcının tarayıcısında               |

Tarayıcı, GET isteğinin cevabından kendi JavaScript verisini oluşturuyor.

Dolayısıyla:

- React state’ini değiştirmek, kendiliğinden backend’e veri yazmaz.
- Backend’de veri değişmesi, tarayıcıdaki state’i kendiliğinden yenilemez.

Aradaki iletişimi HTTP istekleriyle kuruyoruz.

**Props ile state farkı da şöyle:**

| Kavram    | Anlamı                                          |
| --------- | ----------------------------------------------- |
| **Props** | Bileşene dışarıdan verilen bilgiler             |
| **State** | Bileşenin zaman içinde değişebilen kendi durumu |

Bileşen, aldığı props’u doğrudan değiştirmemelidir. State değişikliklerini ise React’in güncelleme mekanizmasıyla yaparız.

Bir terminolojiyi de doğru yerleştirelim: React’in burada kullandığı güncelleme yaklaşımı **Shadow DOM** değildir. Shadow DOM ayrı bir tarayıcı özelliğidir. React, yeni arayüz sonucunu hesaplar ve gerçek DOM’a gereken değişiklikleri uygular. Bu konuyla bağlantılı olarak *virtual DOM* ve *reconciliation* terimlerini duyacaksın. [React](https://react.dev/learn/render-and-commit?utm_source=chatgpt.com)

Şimdilik bilmen gereken: State değiştiğinde her HTML elemanını tek tek bulup elle güncellemek zorunda kalmıyoruz.

**9. React formundan yeni video gönderelim.**

**`NewVideo.js`** dosyasını oluştur:

```
import React from "react";

class NewVideo extends React.Component {

    constructor(props) {
        super(props);

        this.state = { name: "" };

        this.handleChange = this.handleChange.bind(this);
        this.handleSubmit = this.handleSubmit.bind(this);
    }

    handleChange(event) {
        this.setState({ name: event.target.value });
    }

    async handleSubmit(event) {
        event.preventDefault();

        try {
            const response = await fetch("/api/videos", {
                method: "POST",
                headers: {
                    "Content-Type": "application/json"
                },
                body: JSON.stringify({
                    name: this.state.name
                })
            });

            if (!response.ok) {
                throw new Error(`HTTP ${response.status}`);
            }

            window.location.href = "/react";
        } catch (error) {
            console.error("Video eklenemedi.", error);
        }
    }

    render() {
        return (
            <form onSubmit={this.handleSubmit}>
                <input
                    type="text"
                    value={this.state.name}
                    onChange={this.handleChange}
                />

                <button type="submit">Submit</button>
            </form>
        );
    }
}

export default NewVideo;
```

Burada birkaç yeni bağlantı var.

**Input’un değeri state’ten geliyor.**

```
value={this.state.name}
```

Kullanıcı yazdığında:

```
onChange={this.handleChange}
```

çalışıyor. Metot da yeni değeri state’e koyuyor:

```
this.setState({ name: event.target.value });
```

`event.target`, bu olayın geldiği input elemanı; `value` ise onun güncel değeridir.

Böylece input ile React state’i birlikte ilerler. Buna **controlled input** denir.

**`bind(this)` neden var?**

Bu class yazımında metotları olay işleyicisi olarak verdiğimizde, içlerindeki `this` değerinin bileşen nesnesini göstermesini istiyoruz:

```
this.handleSubmit = this.handleSubmit.bind(this);
```

Bu, JavaScript’in fonksiyon çağrısı ve `this` davranışıyla ilgilidir.

**Form gönderilince `handleSubmit` çalışıyor.**

```
<form onSubmit={this.handleSubmit}>
```

Burada fonksiyonu hemen çağırmıyoruz; form gönderildiğinde çalıştırılması için referansını veriyoruz. Formun gönderilmesi butonla veya uygun durumda Enter tuşuyla gerçekleşebilir.

**`preventDefault()` neyi durduruyor?**

```
event.preventDefault();
```

Tarayıcının formu kendi varsayılan gönderme davranışıyla göndermesini engelliyor. Gönderimi kendi `fetch()` çağrımızla yönetiyoruz.

Bu işlem olayın üst elemanlara yayılmasını durdurmak değildir. O amaç için `stopPropagation()` vardır. [dom.spec.whatwg.org](https://dom.spec.whatwg.org/?utm_source=chatgpt.com)

**`async` ve `await` burada ne sağlıyor?**

Ağ işleminin sonucunu bekleyip devam eden akışı daha kolay okumamızı sağlar:

```

Bekleme sırasında bu fonksiyonun devamı ertelenir; JavaScript’in diğer işleri işlemesine imkân kalır. `await`, tarayıcıyı meşgul eden bir bekleme döngüsü değildir. `async` fonksiyonlar Promise döndürür; `.then(...)` ile de asenkron devam adımları tanımlanabilir. [V8](https://v8.dev/blog/fast-async?utm_source=chatgpt.com)

**1. API yayımladığında istemcilere bir sözleşme sunmuş olursun.**

**2. İstemci hangi sürümü istediğini nasıl bildirebilir?**

Dört temel yöntemimiz var:

| Yöntem                     | Örnek istek bilgisi                  | Temel özellik                                      |
| -------------------------- | ------------------------------------ | -------------------------------------------------- |
| **URL yolu**               | `/api/v2/videos`                     | Sürüm doğrudan adreste görünür.                    |
| **İstek başlığı**          | `API-Version: 2`                     | Adres sabit kalır; sürüm header ile taşınır.       |
| **Query parametresi**      | `/api/videos?version=2`              | Sürüm URL’nin sorgu bölümündedir.                  |
| **Medya türü parametresi** | `Accept: application/json;version=2` | İstenen cevap biçimiyle birlikte sürüm belirtilir. |

Bunlar alternatif yapılandırmalar. Hepsini uygulama ayarlarımıza birlikte eklemeyeceğiz.

Bu dersin sonunda uygulamamızda **header yöntemi ve varsayılan v1** ile devam edeceğiz. Böylece önceki React çağrılarımız aynı sözleşmeyi kullanabilecek.

Spring Framework 7, sürüm bilgisini çözümleme ve controller metotlarını sürüme göre seçme desteği sunuyor. Spring Boot 4 de bu mekanizmayı properties ayarları üzerinden yapılandırmamızı sağlıyor. [spring.io](https://spring.io/blog/2025/09/16/api-versioning-in-spring?utm_source=chatgpt.com)

Burada iki ayrı bilgi tanımlayacağız:

1. **Sürümü isteğin neresinden okuyacağız?**
2. **Hangi controller metodu hangi sürüme hizmet edecek?**

**3. Önce ikinci cevap modelimizi hazırlayalım.**

Mevcut modelimiz:

```
package com.learningspringboot4;

record Video(String name) {}
```

İkinci modelde video adına ek olarak bir açıklama alanımız olsun.

Aynı pakette **`VideoV2.java`** oluştur:

```
package com.learningspringboot4;

record VideoV2(String name, String description) {}
```

Buradaki constructor artık iki değer alır:

```
new VideoV2("Learning Spring Boot 4", "Spring Boot'a giriş")
```

İlk değer `name`, ikinci değer `description` bileşenine gider.

**`VideoV2` ismini vermek tek başına Spring’e sürüm bilgisi tanımlamaz.** Bu, bizim Java tipimizin adı. HTTP isteğinin hangi metoda gideceğini birazdan `version` özelliğiyle belirleyeceğiz.

Bu örnekte açıklama alanının eklenmesi çoğu istemci için geriye uyumlu olabilir. Ayrı v1 ve v2 metotlarıyla sürüm seçme mekanizmasını görünür hâle getiriyoruz.

**İkinci modeli aynı video verisinden üretelim.**

Örneği tamamlamak için mevcut `VideoService` sınıfına şu metodu ekle:

```
public List<VideoV2> getVideosV2() {
    List<VideoV2> result = new ArrayList<>();

    for (Video video : videos) {
        result.add(new VideoV2(video.name(), ""));
    }

    return List.copyOf(result);
}
```

Part 4’teki `List` ve `ArrayList` import’larımız burada da kullanılıyor.

Bu metot, mevcut videoları ikinci cevap modeline dönüştürüyor. Henüz açıklama saklamadığımız için `description` değerini boş metin olarak veriyoruz.

**Küçük Java parantezi: `for` satırı ne yapıyor?**

```
for (Video video : videos)
```

Bunu şöyle oku:

> “`videos` listesindeki her `Video` için, sıradaki elemanı `video` değişkeniyle kullan ve süslü parantezin içindeki işlemi yap.”

Her turda:

```
new VideoV2(video.name(), "")
```

ile yeni bir cevap nesnesi oluşturuyoruz.

- `video.name()`, mevcut record’un adını alır.
- `result.add(...)`, yeni nesneyi sonuç listesine ekler.
- `List.copyOf(result)`, sonucu değiştirilemeyen bir liste olarak döndürür.

Mevcut `videos` listesini değiştirmiyoruz. Aynı verinin ikinci bir sunumunu üretiyoruz.

Örneğin tek bir video için:

**V1 sunumu:**

```
{
  "name": "Learning Spring Boot 4"
}
```

**V2 sunumu:**

```
{
  "name": "Learning Spring Boot 4",
  "description": ""
}
```

Böylece yeni video eklendiğinde her iki listeleme metodu da aynı temel veriyi kullanabilir.

**4. Birinci yöntem: Sürümü URL yolunda taşımak**

Önce URL üzerinden sürümlemeyi inceleyelim.

Controller’daki listeleme metotları şöyle olabilir:

```
@GetMapping(value = "/api/{version}/videos", version = "1")
public List<Video> all() {
    return videoService.getVideos();
}

@GetMapping(value = "/api/{version}/videos", version = "2")
public List<VideoV2> allV2() {
    return videoService.getVideosV2();
}
```

Şu annotation’ı dikkatlice okuyalım:

```
@GetMapping(value = "/api/{version}/videos", version = "2")
```

**`value`**, adres desenini belirtiyor.

**`{version}`**, o konumun değişken bir yol parçası olduğunu söylüyor.

**`version = "2"`**, bu metodun API’nin ikinci sürümüne hizmet edeceğini belirtiyor.

Daha önce tek değer verirken:

```
@GetMapping("/api/videos")
```

yazabiliyorduk. Birden fazla annotation özelliği belirtince, adresi de `value = ...` şeklinde açıkça yazıyoruz.

Şimdi `application.properties` içinde sürümün hangi yol parçasından okunacağını belirtmemiz gerekir:

```
spring.mvc.apiversion.use.path-segment=1
```

Örnek adres:

```
/api/v2/videos
```

Yol parçalarını sayalım:

| İndeks | Parça    |
| ------ | -------- |
| `0`    | `api`    |
| `1`    | `v2`     |
| `2`    | `videos` |

🔴 **Buradaki `path-segment=1`, “API sürümü 1 olsun” demiyor. “Sürümü, indeks numarası 1 olan parçadan oku” diyor.**

Bu nedenle çağrılarımız:

```
curl http://localhost:8080/api/v1/videos
```

```
curl http://localhost:8080/api/v2/videos
```

İlk çağrı `all()`, ikinci çağrı `allV2()` metoduna yönlendirilir.

**Peki URL’deki `v2`, annotation’daki `"2"` ile nasıl eşleşiyor?**

Varsayılan sürüm ayrıştırıcısı, baştaki `v` gibi sayısal olmayan önekleri atlayabilir. Ayrıca `2`, `2.0` ve `2.0.0` değerlerini aynı anlamsal sürüm olarak değerlendirebilir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/accept/SemanticApiVersionParser.html?utm_source=chatgpt.com)

Bu yapılandırmada sürüm URL deseninin bir parçasıdır. Varsayılan sürüm tanımlamak, `/api/videos` adresini kendiliğinden `/api/v1/videos` biçimine dönüştürmez.

URL yöntemi kolay görünür ve terminalden rahat denenir. Ancak istemcilerin kullandığı adresler de sürümlenir; mevcut React kodumuzdaki `/api/videos` çağrılarının buna göre ele alınması gerekir.

**5. İkinci yöntem: Sürümü header içinde taşımak**

Şimdi uygulamamızda kullanacağımız yönteme geçelim.

Adres sabit:

```
/api/videos
```

İstemci, istediği sürümü bir HTTP başlığıyla bildiriyor:

```
API-Version: 2
```

`application.properties` içindeki sürümleme ayarımız şu olsun:

```
spring.mvc.apiversion.use.header=API-Version
spring.mvc.apiversion.default=1
```

Önceki `use.path-segment` ayarını bu yönteme geçerken kaldırıyoruz.

İlk satırın anlamı:

> “Sürüm bilgisini `API-Version` isimli istek başlığından oku.”

İkinci satırın anlamı:

> “İstemci sürüm belirtmezse 1 kabul et.”

`API-Version`, burada seçtiğimiz başlık adı. Spring’e hangi başlığı okuyacağını properties üzerinden bildiriyoruz.

**`ApiController` sınıfımızın bu yöntemle tamamlanmış hâli:**

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ApiController {

    private final VideoService videoService;

    public ApiController(VideoService videoService) {
        this.videoService = videoService;
    }

    @GetMapping(value = "/api/videos", version = "1")
    public List<Video> all() {
        return videoService.getVideos();
    }

    @GetMapping(value = "/api/videos", version = "2")
    public List<VideoV2> allV2() {
        return videoService.getVideosV2();
    }

    @PostMapping("/api/videos")
    public Video newVideo(@RequestBody Video newVideo) {
        return videoService.create(newVideo);
    }
}
```

Burada eski listeleme metodumuzu v1 olarak tanımladık ve v2 metodunu ekledik.

**Aynı GET adresinin iki kez bulunması neden çakışmıyor?**

Çünkü artık eşleştirme koşullarımız arasında sürüm de var:

| HTTP metodu | Adres         | Sürüm | Seçilen metot |
| ----------- | ------------- | ----- | ------------- |
| GET         | `/api/videos` | `1`   | `all()`       |
| GET         | `/api/videos` | `2`   | `allV2()`     |

Spring, bu örnekteki sabit sürüm koşullarını kullanarak uygun metodu seçer. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html?utm_source=chatgpt.com)

Sürüm ayrımını burada **listeleme işlemine** uyguluyoruz. POST işlemimizin gönderilecek veri sözleşmesi hâlâ `{"name":"..."}`.

Şimdi iki sürümü çağıralım:

```
curl http://localhost:8080/api/videos \
  -H "API-Version: 1"
```

```
curl http://localhost:8080/api/videos \
  -H "API-Version: 2"
```

İlkinde yalnızca `name` alanı bulunan videoları, ikincisinde `name` ve `description` alanları bulunan videoları almayı bekleriz.

---

**6. Varsayılan sürüm mevcut React istemcimizi nasıl etkiliyor?**

Part 6’daki kodumuz şöyleydi:

```
const response = await fetch("/api/videos");
```

Bu istek, `API-Version` başlığı göndermiyor.

Şu ayar sayesinde:

```
spring.mvc.apiversion.default=1
```

istek v1 olarak değerlendirilir. React uygulamamız bildiği cevap sözleşmesini kullanmaya devam eder.

Yeni bir istemci ise açıkça v2 isteyebilir:

```
const response = await fetch("/api/videos", {
    headers: {
        "API-Version": "2"
    }
});
```

Bu, mevcut istemciyi korurken yeni bir sözleşme sunmanın somut örneğidir.

**Varsayılan sürüm, desteklenmeyen sürümlerin yerine geçen genel bir yedek değildir.**

Şu iki durumu ayır:

| İstek                                | Davranış                                |
| ------------------------------------ | --------------------------------------- |
| Sürüm belirtilmemiş                  | `default=1` nedeniyle v1 kullanılır.    |
| Açıkça `API-Version: 99` gönderilmiş | Desteklenmeyen sürüm olarak reddedilir. |

Desteklenmeyen sürüm, varsayılan yapılandırmada `400 Bad Request` sonucuna yol açar. Spring bunu v1’e sessizce dönüştürmez. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc-versioning.html?utm_source=chatgpt.com)

---

**7. Üçüncü yöntem: Query parametresiyle sürümleme**

Bu alternatifte controller adresleri yine:

```
@GetMapping(value = "/api/videos", version = "1")
```

ve:

```
@GetMapping(value = "/api/videos", version = "2")
```

şeklinde kalır.

Sürümleme ayarını şu şekilde seçeriz:

```
spring.mvc.apiversion.use.query-parameter=version
spring.mvc.apiversion.default=1
```

Bu yöntemi denerken `use.header` ayarını kaldırırız.

Çağrılar:

```
curl "http://localhost:8080/api/videos?version=1"
```

```
curl "http://localhost:8080/api/videos?version=2"
```

Burada:

- `/api/videos`, isteğin yoludur.
- `?version=2`, sorgu parametresidir.
- Properties’teki `version`, okunacak parametrenin adıdır.

Parametre adını `api-version` olarak yapılandırsaydık, URL’de de `?api-version=2` kullanmamız gerekirdi.

**`version` adının kendiliğinden çalışan özel bir anlamı yok; istemciyle sunucunun aynı isim üzerinde anlaşması gerekiyor.**

Bu yöntemi adres çubuğundan denemek kolaydır. Çok sayıda sorgu parametresi olan API’lerde ise URL’ler daha kalabalık hâle gelebilir.

---

**8. Dördüncü yöntem: Medya türü üzerinden sürümleme**

Bu alternatifte istemci şu başlığı gönderir:

```
Accept: application/json;version=2
```

Bunu şöyle okuyabilirsin:

> “JSON biçiminde, API’nin ikinci sürümüne ait cevabı istiyorum.”

Ayarımız:

```
spring.mvc.apiversion.use.media-type-parameter[application/json]=version
spring.mvc.apiversion.default=1
```

Burada iki önemli parça var:

- `[application/json]`: İlgilendiğimiz medya türü.
- `version`: Bu medya türü üzerinde okunacak parametrenin adı.

Controller metotları yine `/api/videos` adresinde kalır.

Çağrı:

```
curl http://localhost:8080/api/videos \
  -H "Accept: application/json;version=2"
```

**`Accept` ile `Content-Type` farkını hatırlayalım:**

| Başlık         | İstekteki temel anlamı      |
| -------------- | --------------------------- |
| `Content-Type` | Gönderdiğim gövdenin biçimi |
| `Accept`       | Cevapta kabul ettiğim biçim |

Buradaki GET örneğinde, istediğimiz cevap sürümünü `Accept` üzerinden belirtiyoruz.

Medya türüyle sürümlemenin şu biçimini de görebilirsin:

```
Accept: application/vnd.myapp.v2+json
```

Burada sürüm, özel medya türünün adına gömülmüş.

**Bu biçim, bizim yukarıdaki parametre yapılandırmamızla aynı değildir.** Yazdığımız ayar, `application/json` üzerindeki `version=2` parametresini okur; medya türü adının içindeki `v2` bölümünü kendiliğinden ayıklamaz. Farklı biçimler için uygun ek yapılandırma veya özel çözümleme gerekir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/config/annotation/ApiVersionConfigurer.html?utm_source=chatgpt.com)

Bu yöntem cevap biçimiyle sürümü birlikte ifade eder; ancak istemci tarafında daha ayrıntılı başlık yönetimi gerektirir.

---

**9. `required` ve `detect-supported` ayarlarını doğru anlayalım.**

Bölümde geçen iki ayar daha var. İsimleri yakın konulara değinse de görevleri farklı.

**`required`: İstemci sürüm belirtmek zorunda mı?**

Varsayılan sürüm tanımlamadan şu ayarları kullanırsak:

```
spring.mvc.apiversion.use.header=API-Version
spring.mvc.apiversion.required=true
```

sürüm bilgisi olmayan istekler `400` ile reddedilir.

Bu, **`default=1` satırının bulunmadığı ayrı bir yapılandırma örneği**.

Bizim çalışma ayarımızda ise varsayılan v1 var. İstemcinin sürüm belirtmemesini bu varsayılanla karşılıyoruz.

**`detect-supported`: Desteklenen sürümler nereden öğrenilecek?**

```
spring.mvc.apiversion.detect-supported=true
```

Spring’in controller mapping’lerinden sürümleri tespit etmesini sağlar. Bizim örneğimizde:

```
version = "1"
```

ve:

```
version = "2"
```

tanımları bulunduğu için bu sürümler desteklenen sürümler arasında yer alır.

Otomatik tespit yerine açık bir liste kullanmak istersek:

```
spring.mvc.apiversion.detect-supported=false
spring.mvc.apiversion.supported=1,2
```

şeklinde yapılandırabiliriz.

🔴 **`detect-supported=false`, “sürüm doğrulamasını kapat” anlamına gelmez.** Controller’lardan otomatik keşfi kapatır; desteklenen sürümleri açıkça tanımlamamız gerekir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/config/annotation/ApiVersionConfigurer.html?utm_source=chatgpt.com)

Ayrıca bir sürümü desteklenenler listesine yazmak, onun için controller davranışını otomatik üretmez. İsteği karşılayacak uygun mapping ve uygulama kodu da bulunmalıdır.

**10. Uygulamamızda hangi ayarla devam ediyoruz?**

Dört yöntemi gördük. Bizim `application.properties` dosyamızdaki sürümleme ayarları şunlar olacak:

```
spring.mvc.apiversion.use.header=API-Version
spring.mvc.apiversion.default=1
```

Controller’da da header bölümünde verdiğim `/api/videos` adresli v1 ve v2 metotları bulunacak.

Bu çalışmada tek sürümleme yöntemi seçiyoruz. Bu, API’nin kullanımını anlaşılır tutan bir tasarım kararıdır; Spring’in teknik olarak yalnızca tek çözümleyici desteklediği anlamına gelmez.

**Sürümleme mekanizmasının yaptığı işi doğru konumlandır:**

Spring, istekteki sürümü okuyup uygun metoda yönlendiriyor. Eski sözleşmeyi gerçekten koruyan davranışı ise **bizim yazdığımız v1 kodu** sağlıyor.

Örneğin v1 metodunu bırakıp onun döndürdüğü alanları uyumsuz biçimde değiştirirsek, URL veya header üzerinde hâlâ “1” yazması istemciyi korumaz.

Şimdiye kadar `/api/videos` adresine gelen istekleri karşılıyorduk. Bu kez Java kodumuzdan bu adrese HTTP isteği göndereceğiz.

Bu partın sonunda şu satırın arkasında ne olduğunu açıklayabileceksin:

```
videoClient.getVideosV2();

Görünüşü bir Java metot çağrısı. Fakat birazdan kuracağımız yapıda bu çağrı, **HTTP isteği gönderilmesini ve gelen JSON’un Java nesnelerine dönüştürülmesini** sağlayacak.

**Önce Part 7’yi üç kısa cevapla bağlayalım**

- `/api/v2/videos` için `path-segment=1`, segmentlerin sıfırdan sayılmasından kaynaklanıyordu: `api` → 0, `v2` → 1.
- Aynı `GET /api/videos` adresinde, `API-Version` başlığı hangi sürümlü controller metodunun seçileceğini belirliyordu.
- Varsayılan sürümün `1` olması, sürüm belirtilmediğinde devreye giriyordu. Açıkça desteklenmeyen `99` sürümü istendiğinde varsayılana dönmüyorduk.

**1. Backend nasıl client oluyor?**

“Client” ve “server”, uygulamaların üstlendiği rollerdir.

Bir uygulama, gelen HTTP isteğine cevap verirken server rolündedir. Başka bir adrese HTTP isteği gönderirken client rolünü üstlenir.

Örneğin bizim video uygulamamız, başka bir video servisinden bilgi alacak olsaydı:

1. Kullanıcı bizim uygulamamıza istek gönderirdi.
2. Bizim uygulamamız, video servisine yeni bir HTTP isteği gönderirdi.
3. Gelen cevabı işleyip kullanıcıya cevap verirdi.

**Aynı uygulama, bu işlem sırasında iki rolü de üstlenebilir.**

Biz öğrenme örneğimizde ayrı bir uygulama kurmayacağız. Mevcut uygulamamızdaki yeni bir endpoint, yine mevcut `/api/videos` endpoint’imize HTTP üzerinden ulaşacak.

Böylece başka bir servis kurmadan HTTP client davranışını gözlemleyeceğiz. Gerçek projelerde bu hedef, başka bir makinedeki servis de olabilir.

**2. HTTP client desteğini ekleyelim**

Spring Initializr’da **ADD DEPENDENCIES → HTTP Client** seçeneğini ekleyip **EXPLORE** üzerinden Maven bağımlılığını görebiliriz. PDF’teki Şekil 2.10 ve 2.11 bu iki adımı gösteriyor.

Mevcut `pom.xml` dosyamızın `<dependencies>` bölümüne şu bağımlılığı ekliyoruz:

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-restclient</artifactId>
</dependency>
```

Bu işlemin ardından IDE’de Maven projesini yeniden yüklemelisin.

Buradaki araçları birbirine bağlayalım:

| Parça                            | Görevi                                                             |
| -------------------------------- | ------------------------------------------------------------------ |
| `spring-boot-starter-restclient` | İlgili kütüphaneleri ve Spring Boot desteğini projeye getirir.     |
| `RestClient`                     | HTTP isteğini göndermek ve cevabı işlemek için kullanılır.         |
| HTTP Service Interface           | Yapılacak HTTP çağrılarını Java metotlarıyla tanımlamamızı sağlar. |

Biz **`RestClient` ile çalışan bir HTTP Service Interface** kullanacağız.

`RestClient` senkron çalışır. Bizim örneğimizde Java metodu, HTTP işleminin sonucu gelene veya bir hata oluşana kadar bekler. Başarılı olduğunda işlenmiş sonucu döndürür.

**3. İlk yeni Java kavramımız: `interface`**

Önce client kodumuzu görelim. Diğer Java dosyalarımızla aynı pakette `VideoClient.java` oluşturuyoruz:

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.HttpExchange;

@HttpExchange("/api/videos")
public interface VideoClient {

    @GetExchange(version = "1")
    List<Video> getVideosV1();

    @GetExchange(version = "2")
    List<VideoV2> getVideosV2();
}
```

Bunu üç katmanda okuyacağız: **Java sözleşmesi, HTTP bilgileri ve dönüş tipleri.**

**Java tarafı: Bu metotların gövdeleri nerede?**

Şu satıra bak:

```
List<Video> getVideosV1();
```

Şimdiye kadar metotlarımızda genellikle şöyle bir gövde vardı:

```
public List<Video> getVideos() {
    return videos;
}
```

`VideoClient` içindeki metot bildirimi ise `;` ile bitiyor.

Burada şu sözleşmeyi tanımlıyoruz:

> “`VideoClient` türündeki bir nesne üzerinden `getVideosV1()` çağrılabilmeli ve bu metodun dönüş tipi `List<Video>` olmalı.”

**`interface`, bir türün hangi işlemleri sunacağını tanımlamamızı sağlar.** Bu örnekte işlemlerin nasıl gerçekleştirileceğini arayüzün içinde yazmıyoruz.

İki metodumuzun anlamı:

| Metot           | Parametre | Dönüş tipi                           |
| --------------- | --------- | ------------------------------------ |
| `getVideosV1()` | Yok       | `Video` nesnelerinden oluşan liste   |
| `getVideosV2()` | Yok       | `VideoV2` nesnelerinden oluşan liste |

Bu şekilde bildirilen interface metotları zaten `public` kabul edilir; başlarına ayrıca `public` yazmamız gerekmez.

Ayrıca interface’i doğrudan şöyle oluşturamayız:

```
new VideoClient();
```

Çünkü henüz bu sözleşmenin davranışını gerçekleştiren bir nesneye ihtiyacımız var. Birazdan Spring’in oluşturacağı nesne bu görevi üstlenecek.

**HTTP tarafı: Hangi isteği tarif ediyoruz?**

```
@HttpExchange("/api/videos")
```

Bu client’ın metotları için ortak HTTP yolunu tanımlıyor.

```
@GetExchange(version = "1")
```

İlgili metodun **GET isteğiyle sürüm 1’i çağıracağını** belirtiyor.

İkinci metot da aynı yolu kullanıyor, ancak sürüm 2’yi istiyor.

Buradaki önemli ayrım:

| Annotation     | Bu uygulamadaki görevi                                        |
| -------------- | ------------------------------------------------------------- |
| `@GetMapping`  | Gelen GET isteğini karşılayacak controller metodunu tanımlar. |
| `@GetExchange` | Client’ın göndereceği GET isteğini tanımlar.                  |

`getVideosV2` adındaki `V2`, bizim seçtiğimiz bir Java metot ismidir. HTTP sürümünü belirleyen bilgi, **`version = "2"`** değeridir.

**Dönüş tipi tarafı: JSON nerede?**

Mevcut modellerimizi hatırla:

```
record Video(String name) {}
```

```
record VideoV2(String name, String description) {}
```

Sürüm 2 çağrısında sunucudan JSON gelecek. Client altyapısı bu JSON’u okuyup `VideoV2` nesnelerine dönüştürecek.

Böylece Java kodumuzda sonucu şu türle kullanabileceğiz:

```
List<VideoV2>
```

Bu, client kodunda türlerin açık olmasını sağlar. Ancak uzak sunucunun her zaman doğru JSON göndereceğini garanti etmez; iletişim veya dönüşüm sırasında hata oluşabilir.

**4. Spring, `VideoClient` nesnesini nasıl oluşturacak?**

Şimdi `VideoClientConfig.java` dosyamızı ekleyelim:

```
package com.learningspringboot4;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.ApiVersionInserter;
import org.springframework.web.client.support.RestClientHttpServiceGroupConfigurer;
import org.springframework.web.service.registry.ImportHttpServices;

@Configuration
@ImportHttpServices(VideoClient.class)
class VideoClientConfig {

    @Bean
    RestClientHttpServiceGroupConfigurer videoClientConfigurer() {
        return groups -> groups.forEachClient((group, builder) ->
            builder
                .baseUrl("http://localhost:8080")
                .apiVersionInserter(
                    ApiVersionInserter.useHeader("API-Version")
                )
        );
    }
}
```

Bu bölümde birden fazla yeni şey var. Hepsini tek seferde ezberlemeye çalışma; her parçanın yaptığı işi anlayalım.

**`@Configuration`: Yapılandırma sınıfımız**

Bu annotation, sınıfın Spring yapılandırması sunduğunu belirtir. İçindeki `@Bean` metotlarıyla Spring’in yöneteceği nesneler tanımlayabiliriz.

**`@ImportHttpServices(VideoClient.class)`: Client’ı kaydediyoruz**

Burada Spring’e şunu söylüyoruz:

> “`VideoClient` arayüzünü kullanarak bir HTTP client nesnesi oluştur ve bunu bean olarak kaydet.”

Spring, arayüzümüzü uygulayan bir **proxy nesnesi** oluşturur. Bu nesne, metot çağrılarımızı karşılayıp tanımladığımız HTTP işlemlerini gerçekleştirir. Oluşturulan proxy, constructor üzerinden enjekte edilebilir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/service/registry/ImportHttpServices.html?utm_source=chatgpt.com)

“Proxy” kelimesini burada şöyle düşün:

> Ben `getVideosV2()` metodunu çağırıyorum. Çağrıyı karşılayan nesne, bunun hangi HTTP isteğine karşılık geldiğini biliyor.

Arayüzdeki annotation’lar bu isteğin tarifini sağlar; kayıt ve yapılandırma ise o tarifi çalıştıracak nesneyi hazırlar.

**Peki `VideoClient.class` ne demek?**

Bu ifade, Java’da `VideoClient` türünü temsil eden `Class` nesnesini verir.

Burada Spring’e **hangi türü incelemesi gerektiğini** bildiriyoruz. `VideoClient.class` yazmak, API’yi çağırmaz.

**`@Bean`: Bir yapılandırıcı nesne tanımlıyoruz**

Şu metodun dönüş tipine dikkat et:

```
RestClientHttpServiceGroupConfigurer videoClientConfigurer()
```

İsmi uzun, görevi oldukça belirli:

> HTTP service client gruplarının kullanacağı `RestClient` yapılandırmasını özelleştirmek.

Metodun döndürdüğü nesne bir **yapılandırıcıdır**. Spring Boot bu yapılandırıcıyı kullanarak client ayarlarını uygular.

Burada iki ayrı bean’i ayırt et:

| Bean                   | Nasıl oluşuyor?           | Görevi                                              |
| ---------------------- | ------------------------- | --------------------------------------------------- |
| `VideoClient` proxy’si | `@ImportHttpServices` ile | HTTP çağrılarını gerçekleştirmek                    |
| Client yapılandırıcısı | `@Bean` metoduyla         | Client’ın adres ve sürüm gönderme ayarlarını yapmak |

**5. `->` işaretini ve iç içe iki işlemi anlayalım**

Kodumuzun en yoğun kısmı şu:

```
return groups -> groups.forEachClient((group, builder) ->
    builder
        .baseUrl("http://localhost:8080")
        .apiVersionInserter(
            ApiVersionInserter.useHeader("API-Version")
        )
);
```

`->`, Java’nın **lambda** sözdizimidir.

Bu kullanımda lambda, belirli bir işin nasıl yapılacağını kısa biçimde tanımlamamızı sağlar. Java’da tek bir soyut işlem tanımlayan uygun interface türleri için kullanılabilir; bunlara *functional interface* denir.

Bizim yapılandırıcımız bu şekilde kullanılabilen bir türdür. [docs.spring.io](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/service/registry/HttpServiceGroupConfigurer.html?utm_source=chatgpt.com)

İfadeyi dışarıdan içeriye okuyalım.

**Önce dış lambda:**

```
groups -> ...
```

“Spring bana client gruplarını verdiğinde, sağ taraftaki işlemi uygula.”

**Sonra gruplar üzerinde işlem:**

```
groups.forEachClient(...)
```

“İlgili her grubun client yapılandırıcısına eriş.”

**Sonra iç lambda:**

```
(group, builder) -> ...
```

“Bu grubun bilgisi ve client’ı hazırlamak için kullanılan builder geldiğinde, şu ayarları uygula.”

Burada:

- `group`, grubun bilgisini taşır. Bu örnekte onu kullanmıyoruz.
- `builder`, oluşturulacak `RestClient` için ayar yapmamızı sağlar.

Java, bu parametrelerin türlerini kullanıldıkları yerden çıkardığı için tür isimlerini ayrıca yazmadık.

**Builder üzerindeki iki ayar**

```
.baseUrl("http://localhost:8080")
```

İsteklerin temel adresini belirliyor.

```
.apiVersionInserter(
    ApiVersionInserter.useHeader("API-Version")
)
```

Metotta belirtilen API sürümünün, **`API-Version` adlı HTTP başlığına yazılmasını** sağlıyor.

Bu metotlar builder üzerinden zincirleme kullanılabiliyor. Böylece aynı client’a ait ayarları art arda yapıyoruz.

Şimdi parçaları birleştir:

| Bilginin kaynağı           | Değeri                          |
| -------------------------- | ------------------------------- |
| `baseUrl(...)`             | `http://localhost:8080`         |
| HttpExchange(...)          | `/api/videos`                   |
| GetExchange(...)           | GET                             |
| `version = "2"`            | İstenen API sürümü              |
| `useHeader("API-Version")` | Sürümün taşınacağı başlığın adı |

Ortaya çıkan istek:

```
GET /api/videos HTTP/1.1
Host: localhost:8080
API-Version: 2
```

**🔴 Buradaki ana fikir:** `version = "2"` hangi sürümü istediğimizi, `ApiVersionInserter` ise bu bilgiyi HTTP isteğinin neresine yazacağımızı belirler. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/client/ApiVersionInserter.html?utm_source=chatgpt.com)

Bir kapsam ayrıntısını da atlamayalım: `forEachClient` öncesinde bir filtre kullanmadığımız için bu ayarlar ilgili tüm client gruplarına uygulanır. Şu anda yalnızca bizim client’ımız var. İleride farklı adreslere giden client’lar eklersek grupları ayrı yapılandırmamız gerekir. [docs.spring.io](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/service/registry/HttpServiceGroupConfigurer.Groups.html?utm_source=chatgpt.com)

**6. Client’ımızı bir controller içinde kullanalım**

Şimdi `ApiClientController.java` dosyasını ekliyoruz:

```
package com.learningspringboot4;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ApiClientController {

    private final VideoClient videoClient;

    public ApiClientController(VideoClient videoClient) {
        this.videoClient = videoClient;
    }

    @GetMapping(
        value = "/api/videos/client-test",
        version = "1"
    )
    public List<Video> allV1() {
        return videoClient.getVideosV1();
    }

    @GetMapping(
        value = "/api/videos/client-test",
        version = "2"
    )
    public List<VideoV2> allV2() {
        return videoClient.getVideosV2();
    }
}
```

Constructor injection’ı daha önce `VideoService` ile kullanmıştık. Aynı mekanizma burada da çalışıyor:

```
public ApiClientController(VideoClient videoClient)
```

Spring, bu parametreye kendi oluşturduğu `VideoClient` proxy nesnesini verir.

Değişkenimizin türü bir interface olabilir. Önemli olan, verilen nesnenin o interface’in sözleşmesini gerçekleştirmesidir.

**Mevcut sunucu ayarımızı da koruyoruz**

`application.properties`:

```
spring.mvc.apiversion.use.header=API-Version
spring.mvc.apiversion.default=1
```

İki farklı yapılandırma yönünü açıkça görelim:

| Ayar                                | Yön         | Yaptığı iş                    |
| ----------------------------------- | ----------- | ----------------------------- |
| `spring.mvc.apiversion.use.header`  | Gelen istek | Sürümü HTTP başlığından okur. |
| `ApiVersionInserter.useHeader(...)` | Giden istek | Sürümü HTTP başlığına yazar.  |

Aynı başlık adını kullanmaları, iki tarafın anlaşmasını sağlar.

**🔴 Gelen sürüm otomatik olarak kopyalanıyor mu?**

Bu örnekte sürüm eşleşmesini **yazdığımız metot çağrıları** kuruyor:

```
// Gelen sürüm 1 isteğinin seçtiği metot:
public List<Video> allV1() {
    return videoClient.getVideosV1();
}
```

```
// Gelen sürüm 2 isteğinin seçtiği metot:
public List<VideoV2> allV2() {
    return videoClient.getVideosV2();
}
```

Giden isteğin sürümü, çağırdığımız client metodunun GetExchange(version = "...") bilgisinden geliyor.

Bu ayrım özellikle önemli: Başka bir endpoint içinde `getVideosV2()` çağırırsan o çağrı yine sürüm 2’yi ister. Client metodu, gelen isteğin başlığını kendiliğinden devralmaz.

**8. Diğer sürümleme stratejileri client tarafında nasıl karşılık buluyor?**

| Strateji               | Client tarafındaki araç                     |

| HTTP başlığı           | `ApiVersionInserter.useHeader(...)`         |

**1. `null` tam olarak ne demek?**

Şu kodda bir `Video` nesnesi oluşturuyoruz:

```
Video video = new Video("Spring Boot öğreniyorum");
```

`video` değişkeni, oluşturduğumuz nesneye bir **referans** tutuyor. Bu referans üzerinden nesneye ulaşabiliyoruz:

```
System.out.println(video.name());
```

Şimdi farklı bir durum:

```
Video video = null;
```

Burada `video`, herhangi bir nesneye referans vermiyor.

Dolayısıyla şu çağrıyı yaparsak:

```
video.name();
```

Java’nın üzerinde `name()` metodunu çalıştırabileceği bir nesne bulunmuyor. Sonuç:

```
NullPointerException
```

Bu hata için sık kullanılan kısaltma **NPE**.

Şu değerleri birbirinden ayıralım:

| İfade                             | Anlamı                              |
| --------------------------------- | ----------------------------------- |
| `String name = "Spring";`         | İçeriği olan bir metin              |
| `String name = "";`               | Uzunluğu sıfır olan bir metin       |
| `String name = null;`             | Bir `String` nesnesine referans yok |
| `List<Video> videos = List.of();` | Elemanı olmayan bir liste var       |
| `List<Video> videos = null;`      | Bir liste nesnesine referans yok    |

**Boş bir liste üzerinde işlem yapabilirsin. `null` olan bir liste üzerinden nesne metodu çağıramazsın.**

Bu konu nesne referanslarıyla ilgilidir. Örneğin primitive tür olan `int`, `null` değerini alamaz.

Bir önceki Java konularımıza da küçük bir bağlantı: **`final`, bir referansın yeniden atanmasını sınırlar; tek başına onun `null` olmasını engellemez.**

---

**2. Metodun imzası bize yeterince bilgi veriyor mu?**

Şöyle bir metot gördüğünü düşün:

```
Video getFirstVideosByName(String name)
```

İsminden, ada göre bir video aradığını anlayabiliriz. Fakat iki önemli sorunun cevabı açık değil:

- `name` parametresine `null` göndermek kabul ediliyor mu?
- Hiç video bulunamazsa metot `null` döndürebiliyor mu?

**Nullability sözleşmesi**, bu soruların cevabını açıkça ifade eder.

JSpecify, Java’da bu sözleşmeleri ortak anlamlara sahip annotation’larla tanımlamamızı sağlar. Spring Framework 7 de kendi API’lerinde JSpecify kullanır; uygun IDE ve analiz araçları bu bilgileri okuyabilir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/null-safety.html?utm_source=chatgpt.com)

Dört annotation’ı tanıyalım:

| Annotation      | Verdiği bilgi                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `@NonNull`      | Bu tür kullanımında `null` kabul edilmiyor.                                                      |
| `@Nullable`     | Burada `null` bulunabilir; kullanan kod bunu hesaba katmalı.                                     |
| `@NullMarked`   | Belirtilen kapsamda, ilgili tür kullanımları varsayılan olarak non-null kabul edilir.            |
| `@NullUnmarked` | Çevredeki non-null varsayımını kaldırır; işaretlenmemiş türlerin null durumu belirtilmemiş olur. |

`@NullUnmarked`, eski kodu aşama aşama dönüştürürken kullanılabilir. Her şeyi açıkça `@Nullable` yapmış olmaz; **varsayılan sözleşmeyi kaldırır**.

Kullanacağımız annotation’ların paketi:

```
org.jspecify.annotations
```

**🔴 En önemli ayrım:** Bu annotation’lar sözleşmeyi bildirir. JSpecify’ı eklemek, her metoda otomatik olarak çalışma anında bir `null` kontrolü yerleştirmez. Denetim için bunları anlayan IDE veya analiz araçları gerekir. [docs.spring.io](https://docs.spring.io/spring-framework/reference/core/null-safety.html?utm_source=chatgpt.com)

**3. Video arama metodundaki hatayı birlikte bulalım**

Şimdi `VideoService` içinde, **bilinçli olarak hatalı bir sözleşme taşıyan** örneği inceleyelim:

```
import org.jspecify.annotations.NonNull;
```

```
@NonNull Video getFirstVideosByName(@NonNull String name) {
    return videos.stream()
        .filter(n -> n.name().contains(name))
        .findFirst()
        .orElse(null);
}
```

Metot iki söz veriyor:

```
@NonNull Video
```

“Normal biçimde bir sonuç döndürdüğümde, bu sonuç `null` olmayacak.”

```
@NonNull String name
```

“Beni çağırırken `name` parametresine `null` göndermemelisin.”

Fakat son satırda şunu görüyoruz:

```
.orElse(null)
```

Çelişkiyi anlayabilmek için önce bütün zinciri okuyalım.

**`videos.stream()` — Listedeki elemanlar üzerinde işlem kuruyoruz**

`stream()`, listedeki videoları bir işlem akışı üzerinden değerlendirmemizi sağlar.

Burada veri kaynağımız, daha önce oluşturduğumuz bellekteki video listesi.

**`.filter(...)` — Arama koşulunu tanımlıyoruz**

```
.filter(n -> n.name().contains(name))
```

Bu lambdayı şöyle oku:

> “İncelediğin videonun adı, aranan metni içeriyorsa bu video koşulu sağlıyor.”

Parçaları:

| Parça            | Anlamı                                           |
| ---------------- | ------------------------------------------------ |
| `n`              | O anda değerlendirilen `Video`                   |
| `n.name()`       | Videonun adını veren record accessor’ı           |
| `contains(name)` | Video adında aranan metnin bulunup bulunmadığı   |
| `n -> ...`       | Bir video alıp `true` veya `false` üreten lambda |

Burada iki farklı “name” var:

```
n.name()
```

Videonun adı.

```
contains(name)
```

Metoda gönderdiğimiz arama metni.

Örneğin:

```
"Need HELP with your SPRING BOOT 4 App?".contains("SPRING")
```

Sonuç `true` olur. Bu arama büyük/küçük harfe duyarlıdır.

**`.findFirst()` — İlk eşleşmeyi istiyoruz**

```
.findFirst()
```

Koşulu sağlayan ilk videoyu arar. Bizim sıralı liste akışımızda ilk eşleşme bulunduğunda sonraki videoları incelemeye devam etmesi gerekmez. Sonucu `Optional<Video>` olarak verir. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/stream/Stream.html?utm_source=chatgpt.com)

`Optional<Video>` şu iki durumu ifade eder:

- Bir video bulundu.
- Video bulunamadı.

**`.orElse(null)` — Sonuç yoksa ne döneceğini seçiyoruz**

```
.orElse(null)
```

“Video varsa onu ver; yoksa `null` ver.”

Dolayısıyla davranışımız:

| Arama sonucu | Metodun döndürdüğü |
| ------------ | ------------------ |
| Eşleşme var  | Bir `Video`        |
| Eşleşme yok  | `null`             |

Oysa metodun dönüşünde `@NonNull` yazıyor.

**Sözleşme “`null` döndürmem” diyor; uygulama ise bazı durumlarda `null` döndürüyor.**

Bu görselde controller, `@RequestParam String name` ile URL’deki `name` parametresini alıyor. Örneğin:

**5. Her yere `@NonNull` yazmak zorunda mıyız?**

Paketimiz için bir varsayılan tanımlayabiliriz.

Java sınıflarımızla aynı paket dizininde **`package-info.java`** adlı dosyaya şunu yazıyoruz:

```
@NullMarked
package com.learningspringboot4;

import org.jspecify.annotations.NullMarked;
```

Bu özel dosyada bir sınıf gövdesi bulunmaması normal. Burada pakete ait annotation tanımlıyoruz.

Artık bu paketteki somut parametre, dönüş ve alan türlerinde non-null varsayımından yararlanabiliriz:

```
Video getFirstVideosByName(String name)
```

Bu imzada `Video` dönüşü ve `String` parametresi, ayrıca `@Nullable` yazılmadığı için non-null sözleşmesine sahiptir.

**Ama mevcut `orElse(null)` hatamız devam eder.** Varsayılan belirlemek, metodun davranışını düzeltmez.

İki kapsam ayrıntısı önemli:

- Paket annotation’ı alt paketlere otomatik uygulanmaz. Örneğin `com.learningspringboot4.service` için ayrıca kapsam tanımlaman gerekir.
- Yerel değişkenlerin null durumu, analiz araçlarınca onlara atanan değerlerden takip edilir. Bir metoda `null` ataması yazmak, yalnızca paket işaretli diye Java sözdizimi hatasına dönüşmez. [JSpecify](https://jspecify.dev/docs/user-guide/?utm_source=chatgpt.com)

`@NullMarked`, paket dışında sınıf, interface veya metot gibi daha dar kapsamlarda da kullanılabilir.

---

**6. Arama metodunun sözleşmesini nasıl düzeltebiliriz?**

Aradığımız videonun bulunamaması olağan bir durum. Bunu iki farklı biçimde ifade edebiliriz.

Aşağıdakiler **aynı metodun alternatif tasarımlarıdır**; ikisini aynı ad ve parametrelerle birlikte eklemiyoruz.

**Seçenek A — Bulunamadığında `null` dönebildiğini açıkça söylemek**

Paketimiz `@NullMarked` olduğuna göre:

```
import org.jspecify.annotations.Nullable;
```

```
public @Nullable Video getFirstVideosByName(String name) {
    return videos.stream()
        .filter(video -> video.name().contains(name))
        .findFirst()
        .orElse(null);
}
```

Artık sözleşme davranışla uyumlu:

- `name` için non-null bekliyoruz.
- Dönüş değeri `null` olabilir.

Çağıran kod bunu ele almalı:

```
Video found = videoService.getFirstVideosByName("SPRING");

if (found == null) {
    System.out.println("Video bulunamadı.");
} else {
    System.out.println(found.name());
}
```

`else` kolunda `found` değerinin `null` olmadığını biliyoruz.

**Seçenek B — “Sonuç var / sonuç yok” bilgisini `Optional` ile döndürmek**

```
import java.util.Optional;
```

```
public Optional<Video> getFirstVideosByName(String name) {
    return videos.stream()
        .filter(video -> video.name().contains(name))
        .findFirst();
}
```

Dikkat et: `orElse(null)` kaldırıldı.

`findFirst()` zaten `Optional<Video>` üretiyordu. Biz bu sonucu çağıran tarafa taşıyoruz.

Kullanımı:

```
Optional<Video> result =
    videoService.getFirstVideosByName("SPRING");

result.ifPresentOrElse(
    video -> System.out.println(video.name()),
    () -> System.out.println("Video bulunamadı.")
);
```

Buradaki iki lambda:

- `video -> ...`: Sonuç varsa bulunan videoyla çalışır.
- `() -> ...`: Sonuç yoksa çalışır; parametre almaz.

**`Optional.empty()` de bir nesnedir.** İçinde sonuç bulunmadığını temsil eder. `Optional` döndüren bir metodun “sonuç yok” diye `null` döndürmesi beklenmez. Java’nın `Optional` tipi özellikle bu tür metot sonuçları için tasarlanmıştır. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Optional.html?utm_source=chatgpt.com)

Bu arama işlemini ilerletirken **`Optional<Video>` döndüren biçimi tercih ediyorum**. Çağıran taraf, bulunamama ihtimalini dönüş tipinde doğrudan görüyor.

JSpecify ile `Optional` birlikte kullanılabilir: biri null sözleşmelerini bildirir, diğeri sonuç bulunmamasını bir Java nesnesiyle temsil eder.

**7. Listenin kendisi, elemanları ve elemanların alanları**

Şimdi bölümün en dikkat isteyen kısmına geldik.

Üç ayrı soru soracağız:

1. Listenin kendisi `null` olabilir mi?
2. Liste içindeki bir eleman `null` olabilir mi?
3. Eleman olan nesnenin bir alanı `null` olabilir mi?

**Birinci durum: Liste ve elemanlar non-null**

`@NullMarked` kapsamındaki şu alan bildirimini incele:

```
private List<VideoV2> videosV2 = List.of(
    new VideoV2("MATRIX", "Matrix - Reload"),
    new VideoV2("Lord of the Rings", "The Fellowship")
);
```

Sözleşmesi:

- `videosV2`, bir listeye referans verir.
- Listedeki elemanlar `VideoV2` nesneleridir; `null` eleman beklenmez.

Listenin eleman sayısının sıfır olması yine mümkündür. **Non-null olmak, dolu olmak anlamına gelmez.**

**İkinci durum: Liste elemanları `null` olabilir**

Aynı bildirimin eleman türünü şöyle ifade edebiliriz:

```
List<@Nullable VideoV2>
```

Annotation, `<...>` içindeki `VideoV2` türünün önünde. Bu nedenle elemanların null durumunu tanımlar.

Dört olasılığı birlikte görelim. Tablo, `@NullMarked` kapsamındaki alan veya dönüş türleri içindir:

| Tür                                 | Listenin kendisi `null` olabilir mi? | Elemanlar `null` olabilir mi? |
| ----------------------------------- | ------------------------------------ | ----------------------------- |
| `List<VideoV2>`                     | Hayır                                | Hayır                         |
| `@Nullable List<VideoV2>`           | Evet                                 | Hayır                         |
| `List<@Nullable VideoV2>`           | Hayır                                | Evet                          |
| `@Nullable List<@Nullable VideoV2>` | Evet                                 | Evet                          |

Bu ayrım, koleksiyonun kendisiyle içindeki değerleri ayrı değerlendirmemizi sağlar. [JSpecify](https://jspecify.dev/docs/user-guide/?utm_source=chatgpt.com)

**🔴 Burada `List.of(...)` ayrıntısını kaçırmayalım**

Şu tip, elemanların `null` olmasına izin veren bir sözleşmedir:

```
List<@Nullable VideoV2>
```

Ancak `List.of(...)` ve `List.copyOf(...)`, çalışma anında `null` eleman kabul etmez. Annotation, bu metotların davranışını değiştirmez. [docs.oracle.com](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html?utm_source=chatgpt.com)

Dolayısıyla şu örnek hata üretir:

```
List<@Nullable VideoV2> example = List.of(
    new VideoV2("MATRIX", "Matrix - Reload"),
    null
);
```

Null eleman barındırabilen bir liste oluşturmak isteseydik, uygun bir uygulama kullanmamız gerekirdi. Örneğin:

```
List<@Nullable VideoV2> example = new ArrayList<>();
example.add(null);
```

Sözleşmenin izin verdiği değerlerle, kullandığımız koleksiyon uygulamasının kurallarını birlikte düşünmeliyiz.

**Üçüncü durum: Nesne var, açıklaması bulunmayabilir**

Modelimizi şöyle tanımlayalım:

```
package com.learningspringboot4;

import org.jspecify.annotations.Nullable;

record VideoV2(
    String name,
    @Nullable String description
) {}
```

Burada:

- `name` için non-null sözleşmesi var.
- `description` için `null` kabul ediliyor.

Örneğin:

```
VideoV2 video = new VideoV2("MATRIX", null);
```

`video` bir nesneye referans veriyor. Sadece açıklama değeri `null`.

Bu nedenle:

```
video.name()
```

ile:

```
video.description().length()
```

aynı güvenceye sahip değil. İkinci ifadede açıklamanın bulunmamasını ele almamız gerekir:

```
String description = video.description();

if (description != null) {
    System.out.println(description.length());
}
```

**Liste elemanına `@Nullable` yazmak, nesnenin alanlarını kendiliğinden nullable yapmaz. Her seviyenin sözleşmesi ayrıdır.**

**Önce Part 9’un üç sorusunu cevaplayalım**

**1. `@NonNull` dönüş ile `orElse(null)` neden çelişiyor?**

`@NonNull`, metodun normal dönüşünde `null` vermeyeceğini bildiriyor. `orElse(null)` ise sonuç bulunamadığında `null` döndürüyor.

Annotation eklemek bu davranışı değiştirmiyor. Uygulamayı ve sözleşmeyi birbirine uygun hâle getirmemiz gerekiyor.

**2. `List<@Nullable VideoV2>` ne söylüyor?**

Bizim `@NullMarked` kapsamımızda:

- Listenin kendisinin `null` olmaması bekleniyor.
- Listenin elemanları `null` olabilir.
- `VideoV2` nesnesinin alanlarının null durumu, o alanların kendi bildirimleriyle belirleniyor.

Örneğin `description` alanının nullable olması için bunu record içinde ayrıca belirtiyoruz.

**3. `Optional.empty()` ile `null` arasındaki fark ne?**

`Optional.empty()`, “sonuç bulunamadı” durumunu temsil eden bir nesnedir. Üzerinde `isEmpty()` veya `ifPresentOrElse(...)` gibi işlemleri kullanabilirsin.

`null` üzerinde ise bir nesne metodu çağıramazsın.

**1. Önce API’mizin davranışını belirleyelim**

Şu isteği karşılamak istiyoruz:

```
GET /api/videos/get-first-by-name?name=SPRING
API-Version: 1
```

Bu endpoint, adında verilen metni içeren **ilk videoyu** döndürecek.

Bu çalışma için şu sözleşmeyi seçiyoruz:

| Durum                                               | HTTP cevabı               |
| --------------------------------------------------- | ------------------------- |
| Video bulundu                                       | `200 OK` ve video bilgisi |
| Video bulunamadı                                    | `404 Not Found`           |
| Arama metni boş veya yalnızca boşluklardan oluşuyor | `400 Bad Request`         |
| `name` parametresi hiç gönderilmedi                 | `400 Bad Request`         |

Buradaki `404`, **tek bir video döndüren bu endpoint için seçtiğimiz davranış**. Liste döndüren bir arama endpoint’inde sonuç bulunmadığında `200` ve boş liste dönmek de uygun bir tasarım olabilir.

Önemli olan, davranışı önceden belirleyip tutarlı uygulamamız.

**2. Servisimizin görevi: Videoyu aramak**

public Optional<Video> getFirstVideosByName(String name) {

Gerekli import:

| Durum              | Java tarafındaki sonuç            |
| ------------------ | --------------------------------- |
| Eşleşme bulundu    | İçinde `Video` bulunan `Optional` |
| Eşleşme bulunamadı | Boş `Optional`                    |

Servis burada arama işlemini gerçekleştiriyor.

**HTTP durum koduna henüz karar vermedik.** Birazdan controller, servisten aldığı sonucu HTTP cevabına dönüştürecek.

Bu ayrım sayesinde aynı servis metodunu başka bir Java kodundan da kullanabiliriz.

**3. HTTP cevabını kontrol etmek: `ResponseEntity`**

Şimdiye kadar controller’dan doğrudan şöyle bir değer döndürüyorduk:

```
public List<Video> all()
```

Spring MVC, döndürdüğümüz listeyi JSON’a çevirip HTTP cevabına yazıyordu.

Bu kez durum kodunu da sonuca göre belirlemek istiyoruz. Bunun için `ResponseEntity` kullanabiliriz. Bu tür, HTTP cevabının **durum kodunu, başlıklarını ve gövdesini** ifade etmemizi sağlar. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responseentity.html?utm_source=chatgpt.com)

Şu dönüş tipini okuyalım:

```
ResponseEntity<Video>
```

Anlamı:

> “Gövdesinde bir `Video` taşıyabilen HTTP cevabı.”

`<Video>`, gövde verisinin Java türünü gösteriyor. Bazı cevaplarda gövde göndermemeyi de seçebiliriz.

Şimdi mevcut `ApiController` sınıfına şu metodu ekleyelim. Part 9’daki görselden aynı adresi karşılayan deneme metodunu eklediysen, onu bu sürümle değiştir:

```
@GetMapping(
    value = "/api/videos/get-first-by-name",
    version = "1"
)
public ResponseEntity<Video> getFirstByName(
        @RequestParam("name") String name) {

    if (name.isBlank()) {
        return ResponseEntity.badRequest().build();
    }

    Optional<Video> result =
        videoService.getFirstVideosByName(name);

    return ResponseEntity.of(result);
}
```

Bu metot için gereken yeni import’lar:

```
import java.util.Optional;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.RequestParam;
```

`GetMapping` import’u ve constructor’dan aldığımız `videoService` alanı zaten controller’ımızda vardı.

Şimdi kodu açalım.

**`@RequestParam("name")`: İstekteki değeri Java parametresine bağlıyoruz**

```
@RequestParam("name") String name
```

Şu istekte:

```
?name=SPRING
```

Java metodundaki `name` parametresinin değeri:

```
"SPRING"
```

olur.

`@RequestParam`, varsayılan olarak parametrenin gönderilmesini zorunlu tutar. [docs.spring.io](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestparam.html?utm_source=chatgpt.com)

**`isBlank()`: Gönderilmiş değerin içeriğini kontrol ediyoruz**

```
if (name.isBlank()) {
    return ResponseEntity.badRequest().build();
}
```

Parametre gönderilmiş olabilir ama içeriği şöyle olabilir:

```
""
```

veya:

```
"   "
```

Bu durumda:

```
ResponseEntity.badRequest()
```

`400 Bad Request` durumunu seçer.

```
.build()
```

Gövde eklemeden cevap nesnesini oluşturur.

Buradaki `return`, metodun çalışmasını o noktada bitirir. Dolayısıyla **boş aramada servis çağrısına ulaşmayız.**

**Servisten sonucu alıyoruz**

```
Optional<Video> result =
    videoService.getFirstVideosByName(name);
```

Burada bildiğimiz Java metot çağrısını yapıyoruz. Servis, bellekteki listeyi arayıp sonucu döndürüyor.

**Sonucu HTTP cevabına dönüştürüyoruz**

```
return ResponseEntity.of(result);
```

Bu yardımcı metodun davranışı:

| `result`         | Oluşturulan cevap          |
| ---------------- | -------------------------- |
| İçinde video var | `200 OK`, gövdede video    |
| Boş              | `404 Not Found`, gövde yok |

Bu dönüşüm, `ResponseEntity.of(...)` metodunun tanımlı davranışıdır. [docs.spring.io](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/http/ResponseEntity.html?utm_source=chatgpt.com)

**🔴 `Optional.empty()` kendi başına HTTP 404 üretmez. Biz controller’da `ResponseEntity.of(...)` kullanarak bu karşılığı seçiyoruz.**
